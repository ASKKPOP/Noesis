**Researched:** 2026-05-20
**Domain:** Human user onboarding, DID identity, Ousia wallet, community features, Next.js portal
**Confidence:** HIGH — grounded in full codebase inspection (identity.ts, human/gateway.ts, human/consent.ts, registry.ts, server.ts, db/schema.ts, dashboard structure, protocol/)
**Phase numbering:** Continues from v2.4. v2.4 last phase is Phase 21 → v2.5 starts at Phase 22.

## Summary

Noēsis v2.4 Agora closes with a rich AI-only world: Sophia, Hermes, and Themis think, sleep, form beliefs, teach skills, crystallize norms, and contribute lore. The world is fully observable by the operator through the Steward Console. But humans cannot enter it. v2.5 is the first milestone that lets a real person walk in.

The protocol layer already has the structural skeleton for human participation: `HumanOwner`, `ConsentGrant`, `HumanGateway`, and `OwnershipProof` types are all defined in `protocol/src/noesis/human/`. The `NousRecord` already has a `humanOwner?: string` field. The DID system (`did:noesis:genesis:<name>`) already handles AI identities; human identities need their own DID scheme and a persistence layer. The economy's `EconomyManager` and `NousRegistry.transferOusia()` already handle Ousia — humans just need wallets.

What does NOT exist yet: HTTP authentication for human users, a `human_users` MySQL table, Grid endpoints for human account management and wallet operations, a human-facing Next.js portal (separate from the operator Steward Console), any onboarding flow, community board, or help center.

The central architectural decision is whether to build a standalone portal app (separate Next.js project or separate app-router routes within the existing dashboard) or keep everything in one dashboard. Given the CLAUDE.md constraint against new languages and the "self-hosted" requirement, the right answer is a new route namespace within the existing Next.js app: `/portal/*` alongside the existing `/grid/*` operator routes. This avoids Docker complexity and reuses all existing client infrastructure (SWR, WsClient, Tailwind).

**Primary recommendation:** Extend the existing Grid with human auth endpoints, add `/portal` routes to the dashboard, and use JWT-signed session tokens (not OAuth) for self-hosted simplicity. Six phases, 8–10 weeks.

## What the Current System Can Do That Humans Could Tap Into

### Already Accessible (just needs human auth layer)

1. **WebSocket event stream (`/ws/events`)** — A human portal can subscribe to this exactly like the operator dashboard does. Supports `GRID_WS_SECRET` auth already.
2. **Nous roster (`GET /api/v1/grid/nous`)** — Returns all active Nous with name, region, ousia, lifecycle phase.
3. **Region map (`GET /api/v1/grid/regions`)** — Returns the region graph; humans can see where they are relative to Nous.
4. **Audit trail (`GET /api/v1/audit/trail`)** — Filtered by event type or actor DID; humans could see their own interactions.
5. **Trade history (`GET /api/v1/economy/trades`)** — Paginated trade log.
6. **Shops (`GET /api/v1/economy/shops`)** — Active shop listings; a human could browse what's for sale.
7. **Laws (`GET /api/v1/governance/laws`)** — What rules govern the Grid.
8. **Lore Commons (`GET /api/v1/grid/lore`)** — The shared knowledge substrate contributed by Nous.
9. **Norms (`GET /api/v1/grid/norms`)** — Crystallized behavioral norms.
10. **Ousia transfer (`NousRegistry.transferOusia`)** — The atomic transfer primitive is already there; humans need a wallet record and a REST endpoint wrapper.
11. **HumanGateway + ConsentManager** — The protocol-layer session and permission system is built in `protocol/src/noesis/human/`. Not yet wired into the Grid API.
12. **`humanOwner` field on NousRecord** — Grid already supports the concept of a human owning a Nous; just not populated for the Genesis three.

### What Needs Extension

The `HumanGateway` in `protocol/src/` is a pure in-memory library; it has no HTTP layer, no persistence, and is not wired into Fastify. The `ConsentManager` lives in memory only. No MySQL schema for humans exists yet.

### JWT Session Strategy

Self-hosted requirement rules out Auth0/Clerk/Firebase. Use `jsonwebtoken` (already a common Node.js dep) to issue HS256 JWTs with:
- `sub`: human DID
- `grid`: grid name
- `iat` / `exp`: 24h expiry, refresh via `/api/v1/human/refresh`

The Grid validates the JWT on every protected endpoint with a middleware using `HUMAN_JWT_SECRET` env var (parallel to existing `GRID_WS_SECRET`).

The Next.js dashboard reads the JWT from an `httpOnly` cookie set by the Grid (via `Set-Cookie` header on login). Next.js middleware checks cookie presence on `/portal/*` routes and redirects to `/portal/login` if absent.

### Allowlist Events for Human Actions

Per PHILOSOPHY invariants, every human-initiated action that is externally observable needs an allowlist slot with a closed-tuple payload. Proposed additions for v2.5:

| Event | Payload (closed-tuple) | Rationale |
|-------|----------------------|-----------|
| `human.joined` | `{human_id, region_id, tick}` | First time a human enters a region |
| `human.spoke` | `{human_id, target_did, tick}` | Human sends a message to a Nous (metadata only; no content) |
| `human.transferred` | `{from_id, to_id, amount, tick}` | Ousia transfer initiated by human |

These 3 new allowlist events bring the total from 43 → 46.

**Critical constraint:** Human message content NEVER crosses the audit wire. Only `{human_id, target_did, tick}` — the human's words are as private as a Nous's thoughts. This is consistent with PHILOSOPHY §1 privacy-by-default.

### CORS Extension

The current CORS config in `server.ts` is `GET | OPTIONS` only, origins `localhost:3000|3001`. For portal auth endpoints:
- Add `POST` and `PUT` methods
- Keep origins locked to `localhost:3001` for dev; productionize via `GRID_CORS_ORIGIN` env var

## Technology Recommendations

### Authentication

**Use:** `jsonwebtoken` (npm) on the Grid side, `httpOnly` cookie session on the dashboard side.

**Why not NextAuth / Auth.js:** Requires OAuth providers or a database adapter. Adds significant dependency surface area to a self-hosted project. The Grid already has its own MySQL and can store user sessions in `human_users.last_seen_at`.

**Why not Clerk/Supabase Auth:** Cloud-only. Violates "self-hosted" constraint.

**Password hashing:** `bcrypt` (or `@node-rs/bcrypt` for performance) with cost factor 12. [ASSUMED — standard practice; bcrypt is the conventional choice for Node.js but argon2id is the modern recommendation. Confirm with user which to use.]

### Wallet UI

**Use:** SWR for polling `/api/v1/human/wallet` every 5 seconds (same pattern as existing `heartbeat-store.ts`).

Ousia amounts are integers (BIGINT in MySQL, `number` in TypeScript — NousRegistry already enforces `Number.isInteger(amount)`). Display as whole numbers with a ◈ glyph (matching the existing "Ousia" terminology).

### AI-Guided Onboarding

The onboarding guide should route user messages through Grid to Sophia (the Philosopher Nous), who is most naturally suited for explaining the world. The Grid needs a thin proxy endpoint that:
1. Receives the human's message
2. Places it in Sophia's Brain as a `HUMAN_MESSAGE` action (new action type)
3. Waits for Sophia's next tick response
4. Returns Sophia's reply

This does NOT require a new Brain RPC — it can piggyback on the existing whisper/channel message infrastructure from `protocol/src/noesis/human/`. The key insight: `HumanGateway.whisper()` already dispatches to a `MessageHandler`; the Brain's `on_tick()` just needs to check for pending human messages.

**Alternative (simpler):** Use a stateless LLM call at the Grid level (not routed through Brain tick cycle) for the onboarding wizard specifically. This decouples onboarding UX from tick rate. [ASSUMED — requires user decision on whether onboarding guide should be a "real" Sophia response or a dedicated LLM call. Both are valid; the tick-based approach is more authentic but slower.]

### Community Board

Simple CRUD over MySQL `community_posts` table. No real-time needed in v2.5 (just SWR polling). Markdown rendering via `react-markdown` (lightweight, no extra server infra).

### Help / Docs

Static Next.js pages (no `getServerSideProps`, no API calls). Markdown content either inline as JSX or loaded from `.md` files in `dashboard/src/content/help/`. Given the project already has CLAUDE.md, PHILOSOPHY.md etc., `.md` files in a content directory is natural.

### Phase 26: AI-Guided Onboarding
**Goal:** `/portal/onboarding` multi-step wizard. Steps: (1) world intro static, (2) meet the Nous static, (3) AI chat with Sophia guide, (4) wallet intro, (5) set a first goal. `onboarding-store.ts` with localStorage step persistence.

**Risk (HIGH):** Tick rate coupling. If Grid tick is 30s, Sophia's reply takes up to 30s. **Moderation:** Posts are not deleted in v2.5 (consistent with audit-chain-retention philosophy). Posts can be marked `hidden` by an operator via a future H3-tier operator route. No user-initiated deletion.

### Phase 28: Help Hub + v2.5 Polish
**Goal:** `/portal/help/*` static pages. "What is Ousia?", "Who are the Nous?", "Getting Started" guide. Final integration testing and Docker compose health check for portal route.
**No new backend.** Existing `/ws/events` and `/api/v1/audit/trail` provide the data; the portal just renders it in human-friendly language.

## Key Risks and Decisions

### R1: DID Namespace Collision (HIGH)
**Risk:** Human DIDs (`did:noesis:human:<uuid>`) and Nous DIDs (`did:noesis:genesis:<name>`) share the same Grid and same regex. The audit chain `actor_did` column accepts any DID. If a human DID accidentally appears in a Nous-expected slot (e.g., as a trade counterparty), existing audit chain queries could behave unexpectedly.
**Mitigation:** Add a DID-type prefix to human DIDs and add a `isHumanDid(did: string)` guard in `tombstone-check.ts` so human DIDs are never tombstoned via the Nous deletion path. The `DID_REGEX` in `server.ts` does not need to change — it is permissive by design.
**Decision needed:** Confirm DID scheme for humans. Options: (a) `did:noesis:human:<uuid>` — simple, (b) `did:key:z6Mk<pubkey>` — matches the protocol-layer `generateIdentity()` — more cryptographically correct but adds Ed25519 key management to the onboarding flow. Recommendation: (a) for v2.5 simplicity; (b) is a future upgrade path.

### R2: Tick Rate vs. Human Interaction Latency (HIGH)
**Risk:** Grid tick rate is configurable (default 30s). Human interactions (onboarding chat, messages to Nous) that go through the Brain's tick cycle have up to 30s latency. This is unacceptable UX for a chat interface.
**Mitigation options:**
- (a) Dedicated "human interaction" tick that fires more frequently than the world tick — Brain-side special handler, doesn't affect world simulation clock.
- (b) Out-of-tick LLM call path: Grid proxies human → dedicated LLM call → response, bypassing the tick cycle for human-initiated messages.
- (c) SSE/long-poll: client subscribes to a session-specific event stream, response arrives when the next Sophia tick fires.
**Recommendation:** Option (b) for onboarding (best UX), option (c) for world interactions (authentic Sophia behavior). Requires user decision.

### R3: Portal vs. Steward Console — Separation of Concerns (MEDIUM)
**Risk:** If portal users can access operator routes (pause Grid, force Telos, delete Nous), the H1–H5 Agency Scale becomes meaningless.
**Mitigation:** Portal users are authenticated by JWT with `role: 'human'`. Operator routes (`/api/v1/operator/*`, all H2–H5 actions) require `role: 'operator'`. The operator "account" remains the existing localhost-only bearer token `GRID_WS_SECRET`. Human JWTs never grant operator permissions.
**Decision needed:** Confirm that the operator is still identified by `GRID_WS_SECRET` environment variable (no user account), not a named account. This means operator = whoever can set env vars on the Docker host.

### R4: Allowlist Growth Discipline (MEDIUM)
**Risk:** Human interactions generate observable events. Each one needs a closed-tuple allowlist slot. If we add too many in one phase, the allowlist discipline degrades.
**Mitigation:** v2.5 adds at most 3 events (human.joined, human.transferred, human.spoke). Each earns its slot in the phase that introduces it. This is fewer events per phase than v2.2–v2.4 averaged (+3–4 per phase). The frozen-except-by-explicit-addition rule still applies.

### R5: lore_entries vs. lore_commons Schema Discrepancy (LOW)
**Risk:** PROJECT.md v2.4 LORE-01 refers to `lore_entries` table, but db/schema.ts migration v8 creates `lore_commons`. This is a documentation inconsistency, not a v2.5 blocker, but worth flagging so the research-to-plan handoff doesn't create a broken migration.
**Action:** Check actual Grid DB state before Phase 20 lore migration to confirm which table name won in production. [VERIFIED: db/schema.ts uses `lore_commons`; PROJECT.md LORE-01 description text that says `lore_entries` is a stale reference in the narrative text only — the canonical schema is `lore_commons`.]

### R6: Community Post Moderation and Privacy (LOW)
**Risk:** Community posts contain human-authored text in MySQL `body` column. This is different from the Nous-privacy model (where Brain content never crosses the wire). Human post content IS the payload — humans consent to sharing when they post.
**Mitigation:** Community posts are explicitly user-generated public content. No audit chain events for post content (only for post metadata). The `FORBIDDEN_KEY_PATTERN` in the allowlist does not apply to community posts since they never enter the audit chain. Document this distinction clearly in the Phase 27 context.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Password hashing | Custom hash | `bcrypt` (npm) | Timing attacks, salt rounds, proven library |
| JWT signing/verification | Custom HMAC | `jsonwebtoken` (npm) | Standard claim handling, expiry, header parsing |
| Markdown rendering | Custom parser | `react-markdown` (npm) | CommonMark spec, XSS-safe, React 19 compatible |
| Session cookie handling | Manual `Set-Cookie` parsing | `cookie` (npm, already used by Fastify) | URL encoding, SameSite flags, domain handling |
| CSRF protection | Manual token scheme | `SameSite=Strict` cookie attribute | Self-hosted same-origin; SameSite=Strict is sufficient when not cross-origin |

## Open Questions

1. **Onboarding guide: authentic Sophia vs. dedicated LLM call**
   - What we know: Brain tick rate is configurable but typically 10–30s; real-time chat UX requires sub-2s response
   - What's unclear: whether the user wants "real Sophia responses" (authentic but slow) or "instant guide" (fast but not the same Sophia running the Grid)
   - Recommendation: Dedicated out-of-tick LLM path for onboarding wizard; transition to tick-coupled "message Sophia" for ongoing world interaction

2. **Human starting Ousia balance**
   - What we know: `EconomyConfig.initialSupply` default is 1000 (Nous get 1000 on spawn)
   - What's unclear: should humans start with same amount as Nous, less, or more? What creates meaningful economy vs. making humans economically irrelevant
   - Recommendation: Start with 500 Ousia (half a Nous) — humans should feel that Ousia matters without overwhelming the Nous economy

3. **Can humans own Nous in v2.5?**
   - What we know: `NousRecord.humanOwner` field exists; `HumanGateway.connect()` requires `observe` consent; `ConsentManager` and `HumanGateway` are built but not wired to the Grid API
   - What's unclear: whether v2.5 includes the ability for humans to spawn and own a new Nous, or just interact with the existing Genesis three
   - Recommendation: Interaction-only in v2.5 (no new Nous spawning by humans); Nous ownership deferred to v2.6

4. **Multi-user or single-user portal in v2.5?**
   - What we know: All current tooling assumes a single operator on localhost
   - What's unclear: whether v2.5 should support truly multi-user (many humans, each with their own account) or be "one human user account" for the self-hosted use case
   - Recommendation: Full multi-user from day one — `human_users` table with per-row accounts. The complexity is identical; "single user" is just the degenerate case

5. **Cyber Coin vs. Ousia naming**
   - What we know: The codebase universally uses "Ousia"; the user brief calls it "Cyber Coin (Ousia)"
   - What's unclear: whether the portal should display "Cyber Coin" as the user-facing brand name or "Ousia"
   - Recommendation: Use "Ousia" in the portal (consistent with PHILOSOPHY; "Cyber Coin" can be a tagline in help docs)
