# Objective

Wire the 3 sole-producer files (from Plan 33-03) into the existing `grid/src/api/portal/auth.ts` HTTP handlers at the 4 call sites required by D-33-A4 / D-33-A5 / D-33-A6:

- **Site 1 — SIWE first-connect block** (inside `if (!human)`): emit `human.identified` + `portal.auth.register` (AFTER existing `appendHumanJoined`)
- **Site 2 — SIWE unconditional login** (after `if (!human)` closes): emit `portal.auth.login` on EVERY SIWE verify success (first-connect AND repeat-connect)
- **Site 3 — Email signup**: compute `email_hash`, emit `human.identified` + `portal.auth.register` + `portal.auth.login`
- **Site 4 — Email signin** (after `valid === true`, before JWT issuance): emit `portal.auth.login` only

This plan touches ONLY `grid/src/api/portal/auth.ts` — a surgical addition. NO changes to: nonce store, JWT issuance, cookie config, SIWE verify logic, password hashing, or the existing `console.warn` (L308-312) / `console.error` (L356) per D-33-E1 + CLAUDE.md §3 Surgical Changes.

**Purpose:** This is the plan that actually "lights up" the `/users` directory + `/humans/[did]/history siwe_sessions` consumer queries. Until this plan ships, the chain stays silent on portal-auth events; consumers always return empty.

**OBS-10 traceability:** Every producer call inserted by this plan invokes `payloadPrivacyCheck` (via the producer file's step 7 / step 9), which reads `FORBIDDEN_KEY_PATTERN` at runtime. The wiring sites that compute `email_hash` (SHA-256) BEFORE the producer call also enforce OBS-10's "no plaintext PII on the wire" boundary at the HTTP handler edge. Listed in `requirements` for traceability.

**Output:** 1 modified file. Approximately +3 import lines + ~28 call-site lines (split across 4 sites). Existing 350+ line auth.ts file mostly untouched.

**Key insight (D-33-A4):** The SIWE first-connect identity_hash REUSES the existing computed `eth_address_hash` (line 121-123) — byte-identical SHA-256 of lowercased ETH address. This is intentional per D-33-A4: it allows correlation between Phase 22 `human.joined` (which already records `eth_address_hash`) and Phase 33 `human.identified` (which records the same value as `identity_hash`). No new createHash call for SIWE; one new createHash call for email (D-33-A5: `sha256(email.toLowerCase().trim())`).

# Threat Model

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| HTTP request (untrusted body) → SIWE/email validation → producer call | The 4 wiring sites are downstream of payload validation (SIWE verify; email regex; password verify). By the time a producer fires, the actor identity is established and the human_did is from the human registry (server-controlled). |
| Producer call → AuditChain → broadcast wire | Producer files enforce closed-tuple discipline; if a wiring site passes a malformed payload, the producer throws TypeError before audit.append. |
| email plaintext (input) → email_hash (chain) | The `sha256(email.toLowerCase().trim())` computation happens at the producer-call boundary in auth.ts. Email plaintext NEVER reaches the producer call — only its hash. |
