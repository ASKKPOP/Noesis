<objective>
Extend the Grid backend to carry `region` and `created_at` through the portal auth layer.

Purpose: Profile page (Phase 24 D-05) and the auth store need `region` and `created_at` from `/me`. Today `/me` returns only `{ did, eth_address }`. This plan adds the MySQL column, wires it into the HumanRecord, and embeds both fields in the JWT so `/me` can return them without a DB lookup.

Output:
- Migration v10: `region VARCHAR(127) NOT NULL DEFAULT 'agora'` column on `human_users`
- `HumanRecord.region: string` and optional `CreateHumanParams.region?: string`
- `HumanRegistry.createHuman` defaults to `'agora'`
- JWT payload carries `region` + `created_at`
- `/me` response returns 4 fields instead of 2
</objective>

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |

| T-24-01-01 | Spoofing | `/me` JWT field injection — attacker crafts JWT with malicious `region` value | mitigate | `jwtVerify` uses ES256 public key; unsigned/tampered tokens rejected before field access |
| T-24-01-02 | Tampering | XSS via region value reaching React | accept | Region value rendered as JSX text node (React escapes automatically); no `dangerouslySetInnerHTML` in profile page |
| T-24-01-03 | Information Disclosure | region value reveals user's assigned region | accept | Region is non-sensitive (`'agora'` default); no PII; no financial impact |
| T-24-01-04 | Elevation of Privilege | New JWT fields bypass existing auth checks | mitigate | Only reading `payload['region']` and `payload['created_at']`; auth check (`if (!token)`) unchanged; no new privilege path |
