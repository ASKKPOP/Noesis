## Summary

The migration is structurally sound where it moves money on `nous_accounts` directly: the marketplace buyer-debit/seller-credit run on the store's own escrow/settle connection via `debitAccountOnConn`/`creditAccountOnConn` (each money leg stays inside the escrow `BEGIN/COMMIT`), the skim runs after settle commits in its own transaction (no nested connection / deadlock), the D-13 gate resolves both parties via `getByExistenceDid` and rejects with the existing `not_found` reason on either null, and `main.ts` injects `NousAccountStore`/`CivicDidStore`/`gridName` into the single production `NousRunner` and the upkeep scanner with an optional-dep pattern that rejects rather than falling back to Ledger B. Conservation holds on the transfer / escrow / agent-trade paths under `BigInt` arithmetic.

The blocker is that two of the three migrated money paths — **upkeep collection (62.6-02)** and the **structure-revenue skim (62.6-01)** — route through `NousAccountStore.chargeToTreasury` → `creditTreasuryWeiOnConn`, which contains a hard SQL defect (duplicate `balance_wei` column) that MySQL rejects with `ERROR 1110`. Proven empirically against the running `noesis-mysql`. Both paths therefore silently no-op in production, and the upkeep scanner swallows the failure with no log. The root line is pre-existing (`wei-ops.ts`, outside the diff) but it is load-bearing for this phase's stated goal, so 62.6-01/02 do not actually work against a real database. Pre-existing conservation/idempotency gaps that the migration re-plumbs onto the unified ledger are also flagged.

## Critical Issues

### CR-01: `chargeToTreasury` rail is broken SQL — migrated upkeep + skim silently never move money

> **✅ RESOLVED 2026-07-10.** Fixed `grid/src/economy/wei-ops.ts:40` — removed the duplicate `balance_wei` column (`INSERT INTO civic_treasury (grid_name, balance_wei, last_updated_tick) VALUES (?, ?, ?)`). Verified on live `noesis-mysql` 8.0: broken form → `ERROR 1110`; fixed form → insert-then-accumulate works (100 → +50 → 150). tsc clean; 185 economy tests green. **Systemic follow-up still open:** the pre-existing `wei-ops.test.ts` passed *with* the bug because it uses the in-memory `accounts-pool` fake — add a real-MySQL (testcontainer or rig) integration test on `creditTreasuryWeiOnConn`/`chargeToTreasury` so this rail (also used by civic-dues, labor-escrow, treasury-wei, and the 62.5-02 spend paths) is exercised against real SQL. Tracked for the operator's decision.

**File:** `grid/src/economy/wei-ops.ts:40` (dependency; consumed by `grid/src/civic/upkeep-scanner.ts:118` and `grid/src/api/routes/market.ts:433`)
**Classification:** BLOCKER
**Introduced vs pre-existing:** Root defect is PRE-EXISTING (`wei-ops.ts` is not in the 62.6 diff; created in commit `d42d7558`). Phase 62.6 newly routes real production money (upkeep 62.6-02, skim 62.6-01) through it, so the phase's migration is non-functional in production.

**Issue:** `creditTreasuryWeiOnConn` lists `balance_wei` twice in the INSERT column list:

```sql
INSERT INTO civic_treasury (grid_name, balance_wei, balance_wei, last_updated_tick)
VALUES (?, 0, ?, ?)
ON DUPLICATE KEY UPDATE ...
```

Verified against the live `noesis-mysql` (8.0.41) on a scratch table with the exact `civic_treasury` schema (`grid_name, balance_bios, last_updated_tick, balance_wei` per `schema.ts:697` + ALTER `:1102`):

```
ERROR 1110 (42000): Column 'balance_wei' specified twice
```

`chargeToTreasury` (`nous-account-store.ts:92`) calls this inside its transaction, so **every** `chargeToTreasury` throws error 1110 (not `insufficient_balance`) and rolls back. Consequences for the two migrated paths:

- **Upkeep (`upkeep-scanner.ts:139-144`):** the error is not `insufficient_balance`, so the branch hits the bare `continue` — the parcel is skipped with **no log line**, `lastUpkeepTick` is not advanced, no treasury credit, no decay. Upkeep is never collected for any owned parcel, forever, invisibly.
- **Skim (`market.ts:450-453`):** caught, logged as `skim_charge_failed`, swallowed. Structure-revenue is never collected and `treasury.structure_revenue` is never emitted.

Conservation is not violated (the whole transaction rolls back — no wei minted or burned), but both migrated features are dead in production, defeating the purpose of 62.6-01/02. Blast radius beyond this phase: `civic-due-store.ts:67`, `labor-escrow-store.ts:64`, `treasury-wei-store.ts:32` use the same rail. This is why the 62.5 reconciliation "proof" only holds against the fake `accounts-pool.ts` — no unit test exercises this statement against real MySQL.

**Fix:**
```ts
await conn.query(
    `INSERT INTO civic_treasury (grid_name, balance_wei, last_updated_tick)
     VALUES (?, ?, ?)
     ON DUPLICATE KEY UPDATE
         balance_wei = balance_wei + VALUES(balance_wei),
         last_updated_tick = VALUES(last_updated_tick)`,
    [p.gridName, p.amountWei.toString(), p.currentTick],
);
```
Add an integration test that runs `chargeToTreasury` against real (or testcontainer) MySQL, not the in-memory fake.

## Warnings

### WR-01: cowork/co-build settlement leaves the agreement stuck in `completed` on any non-`insufficient_balance` error

> **✅ RESOLVED 2026-07-10.** `cowork.ts`: removed the premature `a.status = 'completed'` — settlement now runs while `'claimed'` and status advances to `'settled'` only on success, so a failed settle leaves it retryable (not stuck). Added a `hostDid === worker` short-circuit (self-completion moves no money, cannot IOU yourself → no-op settle, no `invalid_transfer_self` throw). Same self-guard added to `co-build.ts`. Tests: `cowork.test.ts` + `co-build.test.ts` "WR-01 host === worker" cases. tsc clean; 954 civic+api tests green.

**File:** `grid/src/civic/cowork.ts:161-179`, `grid/src/civic/co-build.ts:170-188`
**Classification:** WARNING
**Introduced:** YES (async settlement + narrow catch introduced this phase).

**Issue:** `completeTask`/`completeSubTask` set `a.status = 'completed'` **before** attempting settlement, and the catch only recovers from `insufficient_balance` (→ IOU). Any other throw from `settleWei` is re-thrown. With `funded: true` now hardcoded in the route (`civic-parcels.ts:841`), a host that is also the worker (owner claims and completes their own posted task — `claimTask` allows any board-access role) triggers `NousAccountStore.transfer`'s `invalid_transfer_self` throw, which is not `insufficient_balance`, so it propagates. The route maps it to 409 and the in-memory agreement is left permanently in `completed` (never `settled`, never reverted). `BigInt(amt)` on a fractional `settlement_amount_wei` (a `number`) throws `RangeError` with the same outcome. The old Ledger-B `transferWei(from===to)` did not throw this way — behavior change.

**Fix:** Guard `hostDid === worker` before settling (short-circuit to IOU or reject up front); revert `status` on a failed settle, or only advance status after the money move resolves.

### WR-02: `completeTask` has no status guard — repeat/concurrent `board/complete` can double-pay

> **✅ RESOLVED 2026-07-10.** `cowork.ts` `completeTask`: added `if (a.status !== 'claimed') throw 'cowork_not_completable'` at entry (route maps it to 409) — a settled agreement can no longer be re-completed, so the money move cannot run twice. `co-build.ts` `completeSubTask`: added `if (session.completed.has(node_id)) throw 'cobuild_already_completed'`. Tests assert `settleWei` is called exactly once and the second completion rejects. tsc clean; 954 civic+api tests green.

**File:** `grid/src/civic/cowork.ts:154-200` (route: `grid/src/api/routes/civic-parcels.ts:840`)
**Classification:** WARNING
**Introduced vs pre-existing:** Missing guard is PRE-EXISTING; the sync→async conversion (this phase) widens the concurrency window.

**Issue:** `completeTask` validates host and worker but never checks `status === 'claimed'`. A second POST to `/board/complete` for an already-`settled` agreement re-runs `settleWei`, moving money host→worker a **second** time. With settlement now an `await`ed DB transfer, two concurrent requests both pass the (absent) status check and both `await` a real transfer — an actual double-spend on the unified ledger, not just an in-memory flip.

**Fix:** Reject unless `a.status === 'claimed'` at entry (`throw 'cowork_not_completable'` → 409). Consider an idempotency key on the route.

### WR-03: escrow debits the buyer at accept but there is no `refunded` writer — disputed/frozen wei is stranded

**File:** `grid/src/marketplace/marketplace-store.ts:233-244` (debit) vs `413-455` (dispute freeze); `grid/src/marketplace/settlement-timeout.ts:69-101`
**Classification:** WARNING
**Introduced vs pre-existing:** PRE-EXISTING architecture (Police resolution is Phase 47, unbuilt); now stranding real unified-ledger wei.

**Issue:** `acceptBid` debits the buyer's `nous_accounts` into escrow. Settlement credits seller+treasury (= amount, conserved). But `dispute`/settlement-timeout only freeze the escrow (`escrow_status='frozen'`); `escrow_status='refunded'` is defined in the type (`marketplace-store.ts:53`) and enum (`schema.ts:638`) but **no code ever writes it or credits the buyer back** (grep-confirmed). A disputed/timed-out escrow leaves the buyer's wei debited with no counter-credit until a Police path that does not exist.

**Fix:** Document the stranded-wei invariant (pending Phase 47) and/or implement the refund writer that credits `buyer_civic_did` and sets `escrow_status='refunded'` on timeout, so no path debits without an eventual credit.

### WR-04: IRS-fee math coerces wei `BigInt`→`Number` — precision loss reachable at true-wei magnitudes

**File:** `grid/src/marketplace/marketplace-store.ts:356`
**Classification:** WARNING
**Introduced vs pre-existing:** The line is PRE-EXISTING (unchanged by the diff), but migrating to true wei-denominated balances makes the >2^53 regime reachable.

**Issue:** `const irsFee = BigInt(Math.floor(Number(amountWei) * params.irsFeeRate));` — `Number(amountWei)` loses precision once `amountWei` exceeds ~9.0e15, well within real wei magnitudes (1 ETH = 1e18 wei). Conservation still holds (`sellerPayout = amountWei - irsFee` is exact `BigInt` subtraction), so nothing is minted/burned — only the fee split ratio skews at large amounts.

**Fix:** Compute the fee in integer/`BigInt` space, e.g. basis points: `irsFee = (amountWei * BigInt(feeBps)) / 10000n`.

### WR-05: D-13 reviewer gate reads `proposerBalance` as `Number(bigint)` — precision loss on the gate input

**File:** `grid/src/integration/nous-runner.ts:449`
**Classification:** WARNING
**Introduced:** YES.

**Issue:** `proposerBalance = Number(await this.accountStore.getBalance(...))` coerces a wei `bigint` to `Number`; for balances above ~9.0e15 the value the reviewer sees is rounded. The gate is advisory only (the authoritative check is the exact `BigInt` `transfer`, which throws `insufficient_balance` → `'insufficient'`), so no money is lost or double-moved — but the verdict can disagree with reality near 2^53. `amount` is bounded by `economy.validateTransfer` (positive integer `< maxTransfer`), limiting practical impact.

**Fix:** Keep the balance as `bigint` and compare against `BigInt(amount)` rather than a lossy raw coercion.

### WR-06: upkeep scanner swallows unexpected charge errors with no log

**File:** `grid/src/civic/upkeep-scanner.ts:139-146`
**Classification:** WARNING
**Introduced:** YES (this catch/`continue` shape is new to the migrated path).

**Issue:** On any non-`insufficient_balance` throw from `chargeToTreasury` the scanner does a bare `continue` with no log — exactly what hid CR-01. A hard SQL failure produces zero observability, and the parcel is silently skipped every sweep. A transient DB fault is indistinguishable from correct operation.

**Fix:** Log the unexpected error (`warn` with `parcel_id` + message) before `continue`, mirroring the market skim's `skim_charge_failed` log.
