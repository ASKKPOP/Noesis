<domain>
## Phase Boundary

Phase 62.5 (waves 01–03 ✅) unified the **civic spend paths** (land, community, business-DID, blueprint material, type-B bond) onto Ledger A (`nous_accounts` civic-DID + `civic_treasury`) and retired the birth faucet. A discovery during 62.5-03 found the **remaining** Ledger-B money is not stray call sites but **four whole subsystems** still transacting on `nous_registry.balance_wei` via `NousRegistry.transferWei`. The operator ruled: **do NOT migrate blind** — author a dedicated phase.

**Phase 62.6 delivers:** migrate all four subsystems + the market skim off `nous_registry.balance_wei`/`transferWei` onto `nous_accounts`/`civic_treasury`, preserving atomicity, audit-chain zero-diff (R-31-01), and behavior for funded participants.

**This phase UNLOCKS (does not include):**
- **62.5-04** — one-time data fold of `nous_registry.balance_wei` → `nous_accounts` + removal/deprecation of `NousRegistry.transferWei` (the irreversible cut; operator decision = **ZERO** faucet money, not migrate).
- **62.5-05** — retire the `did:noesis:system:treasury` registry record, delete PR #8 (treasury seed) / PR #11 (census exclusion), add the CI gate forbidding `transferWei`/`nous_registry.balance_wei` as money, clean-DB E2E.

Both 62.5-04 and 62.5-05 remain waves of Phase 62.5 and run **after** 62.6 lands. 62.6 is the precondition: `transferWei` cannot be removed and the `did:noesis:system:treasury` record cannot be retired while these subsystems still write to them.

**Out of scope for 62.6:** the `*_bios`→`*_wei` *rename* (Phase 66), Ousia conflict-tribute (Phase 66), on-chain settlement (Phase 63), the 62.5-04 data fold, the 62.5-05 CI gate. No new schema migration in 62.6 unless research proves one is required to resolve keying (see open question O1).

</domain>

<decisions>
## Implementation Decisions (locked)

### Ledger target
- **D-1 (locked):** Money moves onto **Ledger A** — `nous_accounts.balance_wei` (per civic-DID) for Nous balances, `civic_treasury.balance_wei` for treasury. No bridge, no dual-write. Option A per `migration-plan-unify-ledger-2026-07-10.md`.
- **D-2 (locked):** Reuse the existing transactional rails — `debitAccountOnConn` / `creditAccountOnConn` / `creditTreasuryWeiOnConn` (`grid/src/economy/wei-ops.ts`), `NousAccountStore.chargeToTreasury` / `refundFromTreasury` (added 62.5-02), and `NousAccountStore` atomic **transfer** (credit→debit under `SELECT … FOR UPDATE` on one connection) for Nous→Nous moves. Do **not** invent new money primitives.

### Per-subsystem mapping (locked target; exact call sites in RESEARCH.md)
- **D-3 marketplace** (`grid/src/marketplace/marketplace-store.ts`): buyer-debit/escrow-hold/seller-credit currently on `nous_registry.balance_wei` keyed by `buyer_civic_did`/`seller_civic_did`/`bidder_civic_did` (already civic-keyed — clean swap). Migrate the `SELECT balance_wei FROM nous_registry … FOR UPDATE` / `UPDATE nous_registry SET balance_wei` inside `acceptBid`/settle to `nous_accounts` debit/credit on the same connection/transaction. The IRS-fee→`civic_treasury` already goes to Ledger A; keep it. Escrow semantics (hold at accept, release at settle/refund on cancel) MUST be preserved.
- **D-4 market skim** (`grid/src/api/routes/market.ts:432`): `services.registry.transferWei(settleResult.sellerCivicDid, TREASURY_DID, skim)` → `chargeToTreasury({ civicDid: sellerCivicDid, amountWei: skim })`. Skim follows the seller payout, so it moves in the same phase as D-3.
- **D-5 upkeep** (`grid/src/civic/upkeep-scanner.ts:98`): tick-driven `registry.transferWei(ownerDid, treasuryDid, due)` → owner-debit → `civic_treasury` credit (a `chargeToTreasury` on the owner's civic-DID). This is the path that currently **credits the `did:noesis:system:treasury` Ledger-B record** — retargeting it to `civic_treasury` is what unblocks retiring that record (62.5-05).
- **D-6 co-work / co-build** (`grid/src/civic/cowork.ts:163`, `grid/src/civic/co-build.ts:171`): `transferWei(host → worker)` Nous→Nous settlement → `NousAccountStore.transfer(host → worker)`. These use an injectable `transferWei?` dep seam (default no-op spy) — replace the seam type + default with an account-transfer seam; keep the always-settles-on-completion invariant (D-NH-06) and the credit-ledger IOU recording untouched.
- **D-7 agent trades** (`grid/src/integration/nous-runner.ts:469`): `this.registry.transferWei(this.nousDid, counterparty, amount)` post-review trade settlement → `NousAccountStore.transfer(nousDid → counterparty)`. Preserve the review gate (no transfer / no `trade.settled` on reviewer fail) and the existing `trade.settled`/`trade.rejected` emit contract exactly.

### Invariants (no shortcuts — same as 62.5)
- **D-8:** **No new audit events / no allowlist change.** The *store* the money moves in changes, not the event surface. Keep every sole-producer triad + `payloadPrivacyCheck` intact. If a producer's treasury/counterparty actor value changes, the event name/shape does not.
- **D-9:** **Zero custody.** In-DB civic bookkeeping only — the `grid/src` custody CI ban still passes (no `transferFrom`, no platform keys).
- **D-10:** **Hash-only boundary** — no new payload key; DIDs stay hashed HEX64 where they already were.
- **D-11:** **Deterministic tick** — no new `clock.onTick`. Upkeep already runs on the existing scanner tick; async DB I/O inside it is allowed (blueprint executor precedent, 62.5-02) but must not add a new tick source or reorder settlement within a tick.
- **D-12:** **Atomicity preserved or improved.** Every debit+credit pair executes on one connection inside one `beginTransaction/commit`, rollback-on-failure, no phantom/partial state. This is a strict non-regression vs the current `transferWei` (which is a single in-memory op today).

### Agent-trade settlement (D-13, locked — operator 2026-07-10)
- **D-13:** Agent-trade settle (`nous-runner.ts:469`) resolves existence→civic via `CivicDidStore.getByExistenceDid`; if **either** the trading Nous or the counterparty lacks a civic-DID, the trade **does not settle** — emit `trade.rejected{reason:'not_found'}` (existing allowlisted reason; **no allowlist change**). Inject `NousAccountStore` + `CivicDidStore` into `NousRunner`. Only citizens transact money. Preserve the review gate (no transfer / no `trade.settled` on reviewer fail) and the `trade.settled`/`trade.rejected` emit contract exactly.

### Claude's Discretion
- Exact ordering of the migrated subsystems into waves (parallel where files don't overlap).
- Whether upkeep-scanner's tick loop becomes `async`/awaited or batches charges — as long as D-11/D-12 hold.
- Test-helper strategy: extend the existing `grid/test/helpers/accounts-pool.ts` stateful fake wei-rails pool (built in 62.5-02) rather than mocking per-test.
- Naming of the injectable account-transfer seam replacing `transferWei?` in cowork/co-build.

<open_questions>
## Open Questions — RESEARCH MUST RESOLVE (the "don't migrate blind" risks)

- **O1 — Keying: do all participants have a civic-DID + a `nous_accounts` row?**
  `nous_accounts` is civic-DID keyed; `nous_registry` is existence-DID keyed. Marketplace is already civic-keyed (safe). But:
  - **upkeep** `ownerDid` — is a parcel/structure owner always a citizen (civic-DID) with an account? Or can an existence-only Nous own upkeep-bearing property?
  - **co-work/co-build** `host_did` / `workerDid` — civic-DID or existence-DID? Do co-work participants always hold a `nous_accounts` row?
  - **agent-trades** `nousDid` / `counterparty` in `nous-runner.ts` — the Brain's runtime identity is the **existence-DID**. Traders may be pre-citizen Nous with **no** `nous_accounts` row.
  For each subsystem, determine (a) which DID flavor the code holds, (b) whether an account is guaranteed to exist, (c) the existence→civic resolution path (`civic_did_registry`) if a translation is needed. **Report the truth per subsystem; do not assume.**

- **O2 — Non-citizen fallback policy. ✅ RESOLVED 2026-07-10 (operator): REJECT non-citizens.** Agent-trade settlement (`nous-runner.ts`) resolves the existence-DID → civic-DID via `CivicDidStore.getByExistenceDid` (`civic-did-store.ts:104`, backed by `uq_existence_did`). If **either** party has no civic-DID, the trade does **not** settle — emit `trade.rejected{reason:'not_found'}` (an **existing allowlisted reason** — no allowlist change). Only citizens (civic-DID holders) move money — matches the constitutional citizens-only economy. This is **D-13** below and governs Plan D.

- **O3 — Async propagation blast radius.** `transferWei` is synchronous in-memory; `nous_accounts` ops are async SQL. Trace every caller of the five sites (esp. `upkeep-scanner` tick loop and `nous-runner` on-tick trade settle) to enumerate what must become `async`/awaited, and confirm no on-tick return-contract (`on_tick` action shape) breaks (W-A note: on_tick contract is load-bearing).

- **O4 — Escrow correctness under the new ledger.** Marketplace holds funds in `marketplace_escrow` between accept and settle. Confirm the migrated flow preserves: debit-at-accept, credit-seller-at-settle, refund-buyer-at-cancel, and that a failed settle rolls back to escrow-held (no double-spend, no lost funds).

</open_questions>
