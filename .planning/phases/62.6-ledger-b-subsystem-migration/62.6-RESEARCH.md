## Summary

All four subsystems still move money through the legacy in-memory `NousRegistry.transferWei` (existence-DID keyed, `grid/src/registry/registry.ts:136`) or a raw `nous_registry.balance_wei` SQL update (marketplace). The target rails already exist and are proven by the 62.5-02 civic-route migration.

**The single most important architectural distinction the planner must encode:** marketplace debit/credit MUST run on the store's *existing open connection* via the `*OnConn` helpers (to stay inside the escrow transaction — O4); the other three subsystems open their own transaction via `NousAccountStore` methods (`chargeToTreasury` for upkeep, `transfer` for co-work/co-build/agent-trades). Using `chargeToTreasury` inside marketplace's `acceptBid`/`settle` would open a *nested* connection and break single-transaction atomicity.

**Keying verdict (O1):** marketplace (`buyer_civic_did`/`seller_civic_did`), the skim (`sellerCivicDid`), upkeep (`ownerDid` = purchase `buyerDid` = civic-DID), and co-work/co-build (`host_did`/`worker` from civic-writer routes) are **all civic-DID keyed** and every participant is guaranteed a `nous_accounts` row (62.5-01 creates one on every civic-DID issuance). Only **agent-trades is existence-DID keyed** (`nous-runner.ts` `this.nousDid`/`counterparty` are Brain runtime existence-DIDs) with **no guaranteed account row** — this is the O2 money-policy fork and the only site needing an existence→civic translation.

**Primary recommendation:** Split into four plans. Waves that don't share files run in parallel: (A) marketplace + skim, (B) upkeep [critical path], (C) co-work + co-build, (D) agent-trades [heaviest — needs account-store + civicDidStore injection into NousRunner + the O2 policy decision]. A and B and C touch disjoint files and can proceed concurrently; D is sequenced last and gated on the O2 operator decision.

**Target calls (stay on the store's `conn`, D-12/O4):**

FOR UPDATE` + throws `insufficient_balance`). Map `insufficient_balance` → the existing `insufficient_wei` error so the route's 402/409 mapping and tests stay intact. `buyer_not_found` becomes unreachable (an unfunded civic-DID has a 0-balance row → `insufficient_balance`), mirroring the 62.5-02 `buyer_not_found`→402 retirement.

**Gotchas:**

### 2. Upkeep (`grid/src/civic/upkeep-scanner.ts:98`) — CRITICAL PATH for 62.5-05

**Current code:** in `onUpkeepTick` (async, line 84), for each funded owned non-commons parcel: `const balance = registry.get(ownerDid)?.balance_wei ?? 0` (line 94, reads in-memory NousRegistry = Ledger B), then `if (due > 0 && balance >= due) { registry.transferWei(ownerDid, treasuryDid, due); ... }` (line 96–98). `treasuryDid` = `TREASURY_DID` = `did:noesis:system:treasury` (wired in `main.ts:287`). This is **the last writer to the `did:noesis:system:treasury` Ledger-B record** — migrating it is what unblocks 62.5-05.

**O1 keying verdict — CIVIC-DID, account guaranteed.** `parcel.ownerDid` is set by `parcelRegistry.purchase(addr, buyerDid, ...)` where `buyerDid` is the civic writer's civic-DID (`civic-parcels.ts:147,164`). So owners are civic-DID holders with `nous_accounts` rows. (Note the current `registry.get(civicDid)` reads Ledger B by civic-DID and returns `undefined`→0 for most citizens — that is the split-ledger bug: upkeep silently never charges today. The migration *fixes* it.) No translation needed. Reclaimed parcels get `ownerDid = treasuryDid` (line 127) but `upkeepDue` on a structure-less parcel is 0 so they never hit the charge branch.

**Target call (own transaction — upkeep is not inside a larger tx):**
Replace the read-then-transfer with a try/charge:
```
try {
  await accountStore.chargeToTreasury({ gridName, civicDid: ownerDid, amountWei: BigInt(due), currentTick: tick });
  // funded branch: emit treasury.upkeep_collected, resetCondition, persistUpkeep
} catch (e) {
  if (e.message === 'insufficient_balance') { /* decay-ladder branch (existing else) */ }
  else throw;
}
```
This collapses the affordability read + charge into the atomic `chargeToTreasury` (SELECT FOR UPDATE + debit + treasury credit in one transaction), removing the `registry.get(...).balance_wei` read entirely. The `gridName` must be threaded into `UpkeepScannerDeps` (currently only `registry`/`audit`/`treasuryDid`) — add `gridName` + an `accountStore` (or a `chargeUpkeep(civicDid, amountWei, tick)` seam) to the deps, wired in `main.ts:276` from `pool`.

**Emit unchanged:** `appendTreasuryUpkeepCollected` (line 99) stays — same event, same `owner_civic_did_hash`, same payload. `treasuryDid` param becomes vestigial for the charge (money now goes to `civic_treasury`, not the registry record) but keep the deps field if anything else reads it; the event does not carry the treasury DID.

**O3 async blast radius:** `onUpkeepTick` is **already async** and dispatched fire-and-forget via `void onUpkeepTick(event.tick, this._upkeepScannerDeps)` (`launcher.ts:540`). Adding `await accountStore.chargeToTreasury(...)` inside the existing loop is safe — no new tick source (D-11), no reordering (each parcel still assessed in loop order within the tick). The DB I/O inside the tick loop is the sanctioned blueprint-executor precedent (62.5-02). **Confirm:** the loop must remain resilient — a charge throw on one parcel must not abort the sweep (current code assesses each in isolation; keep per-parcel try/catch).

**Gotchas:**
- The deps facade (`main.ts:276–288`) is composed inline — add `gridName` + `accountStore`/charge-seam there. Keep `registry.transferWei` off the facade once nothing uses it (removal is 62.5-04, but the facade field can drop in this phase since the scanner is its only consumer).
- Upkeep is the ONLY subsystem whose migration is a prerequisite for retiring `did:noesis:system:treasury`; flag its plan as the unblocking deliverable. Market skim (D-4) also wrote to that record and must land too (same-wave with marketplace).

## Open money-policy decision (O2) — FLAG FOR OPERATOR CONFIRMATION

**Question:** When an agent-trade participant (existence-DID) has no civic-DID / no `nous_accounts` row, what happens?

**Evidence:**
- Today, existence-DID Nous CAN trade — `NousRegistry` holds every spawned Nous (existence-keyed) with a balance, so `transferWei` succeeds for pre-citizen Nous. Migrating to civic-keyed `nous_accounts` REMOVES that ability unless we translate or lazily create accounts.
- 62.5-01/02 established the invariant: **accounts are created ONLY on civic-DID issuance** (`registry.ts` REG-01), start at 0, no faucet (D-MONEY-01). `ensureAccount` is idempotent but is deliberately only called at naturalization.
- PHILOSOPHY / civic architecture (D-V3-33 Portal-gating, D-V3-35 Type-B restrictions): economic citizenship is naturalization-gated; money is a civic-DID concept.

**Candidate policies:**
| Option | Behavior | Fit with codebase |
|--------|----------|-------------------|
| (a) lazy `ensureAccount` on first trade | Any existence-DID auto-gets a 0-balance account | Contradicts "accounts created only at civic-DID issuance" (62.5-01). A 0-balance lazy account can't fund a trade anyway → trade fails `insufficient_balance` regardless. Low value. |
| (b) **block: resolve existence→civic; no civic-DID ⇒ `trade.rejected{reason:'not_found'}`** | Only naturalized citizens trade; pre-citizen trades rejected exactly as an unregistered counterparty is today | **Matches** the existing `not_found` reason + the civic-money model. Requires `CivicDidStore.getByExistenceDid`; `null` → reject. **Recommended.** |
| (c) require prior naturalization (hard error surfaced to Brain) | Same as (b) but a distinct reason | Adds a new reason string → risks zero-diff/allowlist. Avoid. |

**Recommendation:** **Option (b).** Resolve `nousDid`→civic and `counterparty`→civic via `CivicDidStore.getByExistenceDid`; if either resolves to `null`, emit `trade.rejected{reason:'not_found', nonce}` (reusing the existing, allowlisted reason — no event/payload surface change, D-8). This preserves the current "counterparty not registered ⇒ not_found" semantics, keeps money a citizens-only civic concept consistent with 62.5, and needs no schema change. **This is a money-policy fork — confirm with the operator before D-7's plan is written.** If the operator instead wants pre-citizen Nous to trade, that reopens the civic-money invariant and is out of scope for 62.6 (escalate).

## Escrow lifecycle (O4) — correctness preserved

The `marketplace_escrow` row is the fund custodian between accept and settle. Migrating buyer/seller balances to `nous_accounts` preserves every leg because each leg stays in ONE transaction with the escrow row mutation:

| Stage | Money leg (new) | Escrow row | Same transaction? |
|-------|-----------------|------------|-------------------|
| **accept** (`acceptBid`) | `debitAccountOnConn(conn, buyerCivic, amount)` | INSERT escrow `held`, mark listing/bid `accepted` | YES — one `conn.beginTransaction/commit` (lines 209/251). Debit-fail (`insufficient_balance`) → `rollback` → no escrow row, no funds moved. |
| **settle** (`settle`) | `creditAccountOnConn(conn, sellerCivic, sellerPayout)` + IRS fee `civic_treasury` | escrow `settled`, listing `settled` | YES — one `conn.beginTransaction/commit` (lines 331/379). Any step throw → `rollback` → escrow stays `held`, seller uncredited, no lost/duplicated funds. |
| **cancel / timeout** (refund) | *see below* | escrow `refunded` | must be one transaction |
| **dispute** (`dispute`) | none (funds stay held/`frozen`) | escrow `frozen` | YES (lines 411/437) — no money move, unaffected by migration |

**Refund path — verify/close a gap:** the buyer's funds are debited at accept and held (conceptually in escrow). On cancel/timeout the buyer must be **credited back** `amount` to `nous_accounts`. Current `marketplace-store.ts` exposes `listExpiredEscrows` (line 454) for the timeout consumer but **the actual refund credit is performed by the caller (settlement-timeout helper / cancel route), not inside the store.** The planner MUST locate the refund site (grep `escrow_status='refunded'` and the timeout consumer) and migrate its buyer-credit from `nous_registry` to `creditAccountOnConn(conn, buyerCivic, amount)` in the same transaction that flips `held→refunded`. **This is a required must-have for the marketplace plan** — a refund left on Ledger B would strand funds after 62.5-04. Flag: confirm exactly one refund writer and one settle writer, no double-credit.

**Double-spend safety:** `debitAccountOnConn` uses `SELECT ... FOR UPDATE` on the buyer's `nous_accounts` row inside the escrow transaction — stronger than the old raw `nous_registry` update (which also FOR UPDATE-locked, line 227). Atomicity is preserved-or-improved (D-12). No leg moves money outside a transaction that also advances the escrow state machine.
