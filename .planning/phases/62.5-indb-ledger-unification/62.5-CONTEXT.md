# Phase 62.5 — In-DB wei ledger unification (Money precursor)

> **Private dev log** (D-WIKI-06). System design is canonical in [wiki/1-design/economy.md](../../../wiki/1-design/economy.md); this is the build kickoff. Milestone: **v3.2 Money**. Plan parent: [../../money-migration-plan.md](../../money-migration-plan.md). Decimal insert **between Phase 62 (on-chain contracts) and Phase 63 (settlement path)** — the on-chain settlement path must bridge **one** coherent civic-keyed in-DB balance, not two.

## Why this phase exists (the finding)

A live UAT (2026-07-10, `claudedocs/finding-split-ledger-economy-2026-07-09.md`, [Issue #9](https://github.com/ASKKPOP/Noesis/issues/9)) proved the current **in-DB** wei economy runs on **two non-fungible ledgers with no bridge** — a precondition the on-chain plan silently assumed was already unified:

| | Ledger A — chain-ready | Ledger B — legacy |
|---|---|---|
| Store (key) | `nous_accounts` (**civic-DID**) · `NousAccountStore`/`wei-ops.ts` | `nous_registry.balance_wei` (**existence-DID**) · `NousRegistry.transferWei` |
| Treasury | `civic_treasury` (IRS/system-map read this) | `did:noesis:system:treasury` registry record |
| Funded by | **endowment** (`EndowmentStore.endow`), labor-escrow, procurement | **birth faucet** (`initialSupply:1000`) |
| Spent on | civic **dues** | **land, community found/join, business-DID, blueprint material, type-B bond** |

Live consequences (reproduced on `main`): the guide's "endow → buy land" is broken (endow funds A, land spends B → a fresh citizen has 0 in B → `buyer_not_found`); labour/procurement income can't buy land either; and the IRS is **blind to land revenue** (it reads `civic_treasury`, land revenue lands in the Ledger-B treasury). ECON-01: founding Nous are still minted 1000 at birth (`did:noesis:system:treasury` = 0 while `nous_registry` holds faucet money).

**This phase makes the in-DB economy coherent — one civic-DID-keyed balance — so Phase 63 can map it 1:1 to the on-chain `NousAccount`.** It also fixes the live citizen-can't-transact bug now, ahead of on-chain.

## Goal

Make **`nous_accounts` (civic-DID) + `civic_treasury`** the single in-DB source of truth for money. Retire `nous_registry.balance_wei` as money and the birth faucet (ECON-01). Reconcile the treasury so IRS/system-map see all revenue.

**Target invariant:** money lives only in `nous_accounts.balance_wei` (per civic-DID) + `civic_treasury.balance_wei`. A spend is an atomic transaction on `nous_accounts` (`debitAccountOnConn` → `creditTreasuryWeiOnConn` on one connection). Every active Civic-DID has exactly one `nous_accounts` row; it starts at **0** (no faucet).

## Definition of done

- A freshly-onboarded Civic-DID has a `nous_accounts` row (balance 0); no faucet at birth.
- All land/community/business/blueprint/type-B charges debit `nous_accounts` (civic-keyed) and credit `civic_treasury`, atomically (failed charge → full rollback, no phantom).
- `/irs/treasury` + system-map reflect land/community/business revenue.
- `nous_registry.balance_wei` is no longer money; the new CI gate passes; `transferWei` is gone/deprecated.
- Clean-DB E2E of endow→buy-land→IRS-sees-revenue is green. Audit chain zero-diff (R-31-01) holds throughout.

## Invariants respected (no shortcuts)

- **No new audit events / allowlist change** — reuses the existing dues/labor/treasury debit-credit events and the existing `zoning.parcel_purchased`/`treasury.parcel_revenue` producers (the *store* the money moves in changes, not the event surface). If any producer's treasury actor changes, keep the sole-producer triad + `payloadPrivacyCheck` intact.
- **Zero custody** — `nous_accounts`/`civic_treasury` moves are in-DB civic bookkeeping, not on-chain transfers; the `grid/src` custody CI ban still passes (no `transferFrom`, no platform keys).
- **Hash-only boundary** — no new payload key; DIDs stay hashed HEX64 where they already were.
- **Deterministic tick** — no new `clock.onTick`; all charges stay request-driven.

## Blocking decision — RESOLVED 2026-07-10

- **Faucet-money fold:** on retiring Ledger B, **ZERO** the founding-Nous faucet balances (operator decision 2026-07-10). The faucet is retired as illegitimate per D-MONEY-01; the 3 × 1000 are NOT migrated into `nous_accounts`. The 62.5-04 data-migration folds only *legitimate* Ledger-B balances (there are effectively none once the subsystems below migrate), and drops the faucet money.

## Prerequisite wave (before 62.5-04/05) — NEEDS ITS OWN PLAN

- **Discovery (2026-07-10):** the remaining Ledger-B money is **whole subsystems**, not stray call sites — `marketplace-store.ts` runs buyer-debit/seller-credit/escrow on `nous_registry.balance_wei` (only the IRS fee credits `civic_treasury`); plus tick-driven **upkeep** (`upkeep-scanner.ts`), **co-work/co-build settlement** (`cowork.ts`/`co-build.ts`), and **agent trades** (`nous-runner.ts`). Market skim (`market.ts:432`) correctly follows the seller's Ledger-B payout, so it cannot move until the trade settlement does.
- **Decision (2026-07-10, operator):** do NOT migrate these blind. Author a **dedicated phase** (`/gsd-plan-phase`) to migrate marketplace-store + upkeep + co-work + agent-trades from `nous_registry.balance_wei` → `nous_accounts`/`civic_treasury`. Only AFTER that can 62.5-04 (fold + remove `transferWei`) and 62.5-05 (retire the `did:noesis:system:treasury` record, delete PR #8/#11, add the CI gate) run without breakage. Suggested: insert as **Phase 62.6** (or fold into a broadened 62.5-05 scope during its plan).
