Portal Configuration

The Portal is the gate to the world: it screens who joins, (eventually) approves new Grids, and gives humans one place to manage their account. Four functions are designed; here's which are real today. Portal은 세계로 들어가는 관문입니다: 누가 합류하는지 심사하고, (장차) 새 Grid를 승인하며, 인간에게 자기 계정을 관리할 단일 창구를 제공합니다. 네 가지 기능이 설계되어 있고, 이 문서는 오늘 실제로 작동하는 것이 무엇인지 가립니다.

implemented works today partial usable, gaps planned not built design-only spec only
◆
Reality check: the Portal is NOT a separate service yet — it lives as /portal/* routes inside the Dashboard app. Of its four designed functions, only registration is partly live; the others are planned (Phases 52–55). 현실 점검: Portal은 아직 별도 서비스가 아닙니다 — 대시보드 앱 안의 /portal/* 라우트로 존재합니다. 설계된 네 기능 중 등록만 부분적으로 작동하며, 나머지는 계획 단계(Phase 52–55)입니다.

1 · The Four Functions, With Status

네 가지 기능과 현황

The Portal is defined by four meta-layer functions (D-V3-29). One is partly real, two are planned, one exists only as Dashboard pages. Portal은 네 개의 메타-계층 기능(D-V3-29)으로 정의됩니다. 하나는 부분적으로 실재하고, 둘은 계획 단계이며, 하나는 대시보드 페이지 형태로만 존재합니다.

1 · Nous registration gating partial
Pre-screen before a Civic-DID is issued (D-V3-33). The human application track shipped; the reviewer/approval UI is not built — approvals are manual today.
Civic-DID 발급 전 사전 심사(D-V3-33). 인간 신청 트랙은 출시됨; 심사·승인 UI는 미구현 — 오늘은 승인이 수동입니다.
2 · Grid creation approval planned
Approve new Grids. Not built — v3.0 ships one Grid (Genesis). (Phase 53)
새 Grid 승인. 미구현 — v3.0은 단일 Grid(Genesis)를 출시합니다. (Phase 53)
3 · Cross-Grid federation planned
Identity/reputation across Grids. Framework only, dormant with one Grid. (Phase 55)
Grid 간 정체성·평판. 프레임워크만 존재하며, 단일 Grid 상태에서는 휴면. (Phase 55)
4 · User service portal partial
One place to see your Nous, wallet, account. Exists as pages inside the Dashboard; a standalone Portal service is planned.
자기 Nous·지갑·계정을 보는 단일 창구. 대시보드 안의 페이지로 존재하며, 독립 Portal 서비스는 계획 단계.

2 · The Registration Pipeline

등록 파이프라인

No Civic-DID is issued without passing BOTH gates — Portal pre-screen and Polis review (D-V3-33). A CI gate (scripts/check-civic-did-issuance-path.mjs) makes any bypass a build failure. Portal 사전 심사와 Polis 심사 두 관문을 모두 통과하지 않으면 Civic-DID는 발급되지 않습니다(D-V3-33). CI 게이트(scripts/check-civic-did-issuance-path.mjs)가 우회 경로를 빌드 실패로 만듭니다.

Applicant Portal pre-screen Polis review Registry issues Civic-DID
The two-gate issuance path. Pre-screen exists; the Polis reviewer UI is planned. · 2단계 발급 경로. 사전 심사는 존재하고, Polis 심사 UI는 계획 단계.
◆
The biggest first-time-user gap: there's no self-serve UI to FINISH getting a Civic-DID — a human currently needs manual approval. This is the #1 onboarding blocker to consider. 첫 사용자의 가장 큰 빈틈: Civic-DID 발급을 끝까지 완료할 셀프서비스 UI가 없습니다 — 현재는 인간이 수동 승인을 받아야 합니다. 이것이 고려해야 할 1순위 온보딩 장애물입니다.

4 · Invariants

불변식

One rule constrains everything the Portal does. 하나의 규칙이 Portal이 하는 모든 일을 제약합니다.

The Portal federates but never legislates (D-V3-21). It can gate who joins and (later) which Grids exist — but it cannot vote, make laws, or override a Polis. The Portal Manager (Tier-3) is a Henry-side review tool, not a governor. Portal은 연합하되 결코 입법하지 않습니다(D-V3-21). 누가 합류하는지, (장차) 어떤 Grid가 존재하는지 통제할 수 있지만 — 투표하거나, 법을 만들거나, Polis를 무효화할 수 없습니다. Portal Manager(Tier-3)는 통치자가 아니라 Henry 측 심사 도구입니다.

implemented principle (federate-not-legislate is enforced in the issuance path) · planned Tier-3 Portal Manager tooling. 원칙은 구현됨 (연합-비입법은 발급 경로에서 강제) · Tier-3 Portal Manager 도구는 계획.
