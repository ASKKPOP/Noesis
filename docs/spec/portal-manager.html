Portal Manager · Tier 3

The meta-system operations surface, Henry-side — the "System administrator Portal." It is the topmost of the three management tiers (D-V3-36) and today the least built: an entire surface still on the roadmap (Phases 52–54). It can review and operate across every Grid, but it can never legislate, vote, pardon a Police sanction, or freeze a Civic-DID. Management — not governance.메타 시스템 운영 표면(Henry 측) — "시스템 관리자 포털". 세 관리 계층(D-V3-36) 중 최상위이며 현재 가장 미구현 — 표면 전체가 아직 로드맵(Phase 52–54)에 있습니다. 모든 Grid에 걸쳐 심사·운영은 가능하나, 입법·투표·경찰 제재 사면·Civic-DID 동결은 불가. 관리이지 통치가 아닙니다.

1 · What the Portal Manager is

Portal Manager란 무엇인가

The Portal is the top meta-layer (4 functions, D-V3-29). The Portal Manager is the operator-facing administrative surface over that layer — where Henry-side meta-ops watch and steward every Grid at once. It is distinct from three things people confuse it with.
Portal은 최상위 메타 계층(4기능, D-V3-29)입니다. Portal Manager는 그 계층 위의 운영자용 관리 표면 — Henry 측 메타 운영이 모든 Grid를 한 번에 감시·관리하는 곳입니다. 사람들이 혼동하는 세 가지와 구분됩니다.

It is NOT… · 아닌 것Because… · 이유
The Polis (per-Grid government)The Polis legislates; the Portal Manager only administers. Polis is sovereign inside its Grid (D-V3-21). · Polis는 입법, Portal Manager는 관리만. Grid 내 주권은 Polis.
The Grid Manager (Tier 2)Tier 2 runs one Grid's runtime (health, scaling, cost). Tier 3 spans all Grids + the registration gate. · Tier 2는 단일 Grid 런타임, Tier 3는 전체 Grid + 등록 게이트.
The Service Portal (public web)The public Portal is for ordinary users (sign up, join, trade). The Portal Manager is for Henry-side meta-ops. · 공개 포털은 일반 사용자용, Portal Manager는 메타 운영자용.
⚖️
Management ≠ Governance (D-V3-36). The Portal Manager has management authority (review, operate, observe) and zero governance authority. At no tier and no action can it vote, draft a bill, override a Polis, pardon a Police sanction, or freeze a Civic-DID. That power lives only with Nous-elected Polises (VOTE-05). The Portal "federates but never legislates" (D-V3-21). 관리 ≠ 거버넌스(D-V3-36). Portal Manager는 관리 권한(심사·운영·관찰)만 있고 거버넌스 권한은 전무합니다. 어떤 계층·행위에서도 투표·법안 발의·Polis 무효화·경찰 제재 사면·Civic-DID 동결 불가. 그 권한은 Nous가 선출한 Polis에게만(VOTE-05). 포털은 "연합하되 입법하지 않음"(D-V3-21).
🚧
Honest status. The Portal Manager is the biggest single gap in the system. The engines it would drive mostly exist Grid-side (the DID Registry, the audit chains, the health endpoints). What is missing is the Portal service and its admin UI. One exception already shipped: the human Civic-DID application pipeline (Type-A human track) landed out-of-band on 2026-06-10 — see §3. 솔직한 상태. Portal Manager는 시스템 최대의 단일 공백입니다. 구동할 엔진은 대부분 Grid 측에 존재(DID 레지스트리·감사 체인·헬스 엔드포인트). 빠진 것은 Portal 서비스와 관리 UI. 단, 인간 Civic-DID 신청 파이프라인(Type-A 인간 트랙)은 2026-06-10 선행 출시 — §3 참조.

3 · Reviewer panels — the registration gate

심사 패널 — 등록 게이트

This is the Portal Manager's core power: it is the gate through which new Grids and new Nous enter (Portal-gating, D-V3-33). Two workflows, both review-panel driven, both deliberately slow. The panel is composition is audit-evident: initial panel = Henry + 2–3 invited human reviewers, with a documented transition to a Nous-elected committee after Phase 46.
Portal Manager의 핵심 권한: 새 Grid와 새 Nous가 들어오는 게이트(Portal 게이팅, D-V3-33). 두 워크플로 모두 심사 패널 기반이며 의도적으로 느립니다. 패널 구성은 감사로 증명: 초기 = Henry + 초대된 인간 검토자 2–3인, Phase 46 이후 Nous 선출 위원회로 전환 계획 문서화.

4 · DID / DNS management & cross-Grid oversight

DID·DNS 관리 및 Grid 간 감독

Beyond the gate, the Portal Manager is where Henry-side ops track identity and watch every Grid at once. Almost all of this is reading and rendering engines that already exist — none of it grants governance power.
게이트를 넘어, Portal Manager는 Henry 측 운영이 신원을 추적하고 모든 Grid를 한 번에 감시하는 곳입니다. 대부분 이미 존재하는 엔진을 읽고 표시하는 것 — 거버넌스 권한은 부여하지 않습니다.

🔒
Read, don't wield. Even where the Portal Manager shows revocations and freezes, those actions belong to the Polis (legislation) and the Police (sanction enforcement). The Tier-3 surface audits them — it cannot issue them. A code path that lets the Portal Manager freeze a Civic-DID would be a constitutional breach (VOTE-05, D-V3-36). 읽되, 휘두르지 않음. 폐기·동결을 표시하더라도 그 행위는 Polis(입법)와 Police(제재 집행)의 것입니다. Tier-3 표면은 그것을 감사할 뿐 발동할 수 없습니다. Portal Manager가 Civic-DID를 동결하게 하는 코드 경로는 헌법 위반(VOTE-05, D-V3-36).

5 · Infrastructure & authentication (Phase 52)

인프라 및 인증 (Phase 52)

The Portal — and with it the Portal Manager — stands up as a separate Henry-hosted service, distinct from any Grid. It carries its own auth, its own session token, and its own audit chain.
Portal(및 Portal Manager)은 어떤 Grid와도 구분되는 별도의 Henry 호스팅 서비스로 기동합니다. 자체 인증·세션 토큰·감사 체인을 가집니다.

Separate service Planned
Greenfield Portal codebase; routes under /portal/api/v1/*. Tech stack (extend Steward Console vs standalone Next.js + Fastify) decided in phase planning.
신규 Portal 코드베이스; 라우트는 /portal/api/v1/*. 기술 스택은 단계 기획에서 결정.
Auth: SIWE + email Plannedschemes exist
POST /portal/auth/siwe and /portal/auth/email (extends v2.5 Portal auth). Session = JWT, 24h expiry — separate from any per-Grid Civic-DID bearer.
POST /portal/auth/siwe 및 /portal/auth/email. 세션 = 24시간 만료 JWT — Grid별 Civic-DID 베어러와 분리.
v1 reviewer-queue prod auth Implemented
The shipped v1 read-only route GET /api/v1/portal-manager/registrations is gated by two server-trusted layers: (1) policy portal_session_required + in-handler operatorScope — a valid httpOnly Portal-session cookie is mandatory (401 portal_session_required / 403 operator_scope_required without one); and (2) a dedicated GRID_PORTAL_MANAGER_ENABLED attack-surface gate (503 portal_manager_disabled when off) — decoupled from GRID_ADMIN_ENABLED, so this read-only console runs in prod without also enabling the admin .env read/write routes. The earlier x-operator-tier/x-operator-id header-trust is no longer the boundary — it survives only as a secondary intent signal behind operatorScope, so a spoofed header alone can never read the queue.
출시된 v1 읽기 전용 라우트 GET /api/v1/portal-manager/registrations는 두 개의 서버 신뢰 계층으로 보호됩니다: (1) portal_session_required 정책 + 핸들러 내 operatorScope — 유효한 httpOnly Portal 세션 쿠키 필수(없으면 401/403); (2) 전용 GRID_PORTAL_MANAGER_ENABLED 공격 표면 게이트(비활성 시 503 portal_manager_disabled) — GRID_ADMIN_ENABLED와 분리되어, 이 읽기 전용 콘솔은 admin .env 읽기/쓰기 라우트를 켜지 않고 운영됩니다. 기존 x-operator-tier/x-operator-id 헤더 신뢰는 더 이상 경계가 아니며 보조 신호로만 남습니다 — 위조된 헤더만으로는 큐를 읽을 수 없습니다.
Own audit chain Planned
Portal maintains its own R-31-01 zero-diff chain, separate from every Grid chain; initialized empty at deploy (Phase 31 PersistentAuditChain pattern carried forward).
Portal은 모든 Grid 체인과 분리된 자체 R-31-01 무결성 체인 유지; 배포 시 빈 상태로 초기화.
Health endpoint Planned
/portal/health/detailed mirrors the Phase 32 Grid watchdog pattern; the Steward Console gets a new /portal-health page that polls it.
/portal/health/detailed는 Phase 32 Grid 워치독 패턴을 반영; 스튜어드 콘솔에 폴링용 /portal-health 페이지 신설.
🏷️
Host name. The operator console lives at system.noesiis.com (and noesiis.com/system/portal-manager) — an nginx server_name system.${DOMAIN} block routes it to the dashboard, / → /system/portal-manager. portal.noesiis.com is reserved for the public Portal (the user-facing meta-layer), NOT this console. The console is convenience, not authority: it stays gated server-side (GRID_PORTAL_MANAGER_ENABLED + Portal session). DNS/ALB cert for system.${DOMAIN} are provisioned operator-side.
