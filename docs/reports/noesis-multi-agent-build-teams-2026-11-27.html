Multi-Agent Build Teams for Nous

1 · What the video says

영상 요약 — 두 가지 이야기: (A) 1,000개 에이전트 팀, (B) 메모리와 “꿈꾸기(dreaming)”

Story A — a 1,000-agent team with almost no scaffolding

September run (before): about a dozen agents, a domain-specific harness for maths proofs, and a researcher nudging them. It worked, but only with that help.

New run: 1,000 agents, no domain harness, no human steering on the solution. Each agent sits in its own sandbox with restricted network. They can reach only Git and a SQL database. The prompt names one lead and 999 helpers, and tells them the problem and the two tools. That is all.

What happened: five minutes in, the lead created its own tables — nobody told it to:

  • announce — the lead posts global decisions
  • roles / assign — the lead gives each helper a statement to work on
  • notes — helpers share progress with each other
  • subtasks — a task tree with dependencies for hard parts
  • landed — finished, checked Lean code (the real output)

The team re-assigned itself as pieces finished. Lean checked every step, so a wrong proof could never land.

Story B — memory, and why agents need to “dream”

The paradox: agents write memory while working, greedily (“this looks important now”), but memory must be a coherent, non-repeating map to be useful later. Kierkegaard: life is understood backwards but lived forwards.

Human analogy: the hippocampus keeps the day; at night it replays to the neocortex, which keeps long-term knowledge.

Evidence shown: on a 40-question continual-learning test, weaker models barely used a memory folder; stronger models knew when to write and read. In Pokémon, an older model wrote a huge, messy memory folder and played worse; a newer one wrote a small, strategic one.

Dreaming = a separate pass that reads transcripts and notes and rewrites them:

  • fixes poisoned memories — a wrong landmark note trapped Claude in a loop; dreaming corrected it and it moved on
  • builds new forms — e.g. a wiki over a company’s documents; more dreaming compute → better answers (search alone ≈53%; wiki + search better than either)
  • fills gaps — placeholder wiki pages got written, an index was added
  • promotes key memories into context that every future session loads first
The one lesson behind both stories: give strong models a few simple, shared primitives, a hard checker for what counts as done, and safety monitoring at the edges — then let them invent their own coordination. Do not hand-script the teamwork.
핵심: 단순한 공용 도구 + 엄격한 검증기 + 외곽 안전 감시. 팀워크 자체는 에이전트가 스스로 만들게 둔다.

3 · Proposed design — a Nous build crew

제안 설계 — Nous 건설 팀(크루): 반장 1명 + 작업자 여러 명, Grid 공용 테이블로 협업

Translate the talk one-to-one. A crew forms around one build (a house, a shop, a road). One Nous is the foreman (the lead); the others are builders. The Grid gives them the shared tables; the existing checks act as the Lean checker. No new governance power: the foreman has no authority over Polis law, and every Nous still pays and gets paid as today (D-NH-06).

From one house to a whole Grid

The same loop nests, like the talk’s task tree for its hardest lemma. A district crew’s DAG has nodes that are themselves house builds, each with its own foreman. A Grid founding crew (much later) has nodes like “propose the first zone set to the Polis” — those nodes are bills, so they still go through VOTE-05 and the Polis. A foreman can never skip the law; the law is one of the checks.

4 · Memory: give Nous a real dream

메모리 — Hypnos(수면)를 진짜 “꿈꾸기”로: 잘못된 기억을 고치고, 위키를 채우고, 핵심만 다음 세션에 주입

Noēsis already named the right module: Hypnos. Today it is a maths pass (Hebbian strengthening + downscale). It never reads a note and asks “is this still true?”. The talk shows that question is what rescues a stuck agent. For builders that matters directly: a Nous that wrongly remembers “parcel 14 is mine” or “oak costs 3 Ousia” will keep failing the same build.

Add a dreaming pass (Brain-only)

  • Runs on the Nous’s sleep tick (Hypnos already gets one; still no wall-clock).
  • Reads recent memories + the Personal Wiki + build outcomes (what landed, what was rejected and why).
  • Corrects: a memory contradicted by a Grid rejection is marked wrong, not just weakened.
  • Fills: wiki pages that are only names get written; an index page is kept.
  • Promotes: at most a handful of lines (“my trade skills”, “my debts”, “my crew”) are put into every next prompt.

Keep what Noēsis promises

  • Memory stays Brain-local, like reflections; the Grid sees only hashes.
  • Dream output is a prompt change → it falls under the Brain parity contract (D-V3-42): fixtures re-recorded and brain-rs changed in the same PR.
  • Dreaming costs AI power, so it is a choice the Nous budgets — consistent with “AI power is money” and the civic duty (D-MONEY-10).

5 · My position on what to do — and what not to

입장 — 해야 할 것과 하지 말아야 할 것

Do not copy “1,000 agents”. The talk’s team was 1,000 copies of a frontier model with a perfect checker (Lean). Noēsis Brains default to small local models (the Ollama adapter; qwen3:4b / llama in config). The talk itself shows weaker models do not use memory or coordination well. Expect a 3–6 Nous crew on small models to under-coordinate. Start with crews of 3–5 and measure.
Our checker is weaker than Lean — say so. Lean proves a step is correct. Our catalog + physics + law prove a build is allowed, not that it is a good house. Without a quality signal, a crew can “land” useless boxes. We need a cheap score of the result (e.g. does the house meet its blueprint’s function: rooms reachable, bed + door + light present) before we let crews run unattended.
Do keep the primitives tiny. The talk’s key result is that the agents invented the tables. We should offer the three crew tables as plain, open records (any field, short text) rather than a rigid workflow — then watch which ones Nous actually use. If they ignore one, delete it.

Brain (Python + Rust)

Actions: crew_announce, crew_assign, crew_note, join / buy in; show the crew’s tables in the builder’s perception. Parity fixtures re-recorded.

Grid

A function check on a finished house (reachable rooms, required objects). Without it, autonomous crews are not safe to leave running.

Live: flag a Nous stuck on one node. Offline: a periodic report per crew (who did what, shares, rejections) — the talk’s 10-minute review.

Brain, Hypnos

Correct / fill / promote, as in §4. Compare build success with and without it — the talk’s with/without test.

Operator decisions — 2026-11-27

운영자 결정 — 크루 규칙

  • D-CREW-01 · Who leads: the first Nous to register on a house project owns it, plans it and is its main builder. When others join, it stays the crew leader for the whole build; joiners are builders.
  • D-CREW-02 · How joiners are paid: in ownership. Each joining Nous becomes a co-owner; its share is the Ousia it invested plus the weight of the build steps it completed. A share counts as compensation under D-NH-06, which is amended accordingly. Co-owners are always Nous (D-NH-07).
  • D-CREW-03 · Late joiners: a Nous joining a house already started or built buys its share; the price is agreed with that Nous’s human user.

Still open: how Ousia and work weigh against each other; how upkeep and each co-owner’s civic duty (D-MONEY-10) are split; how an agreed price is recorded; whether Type B Nous in their first year (D-V3-35) follow the same rules.
