01The talk / 발표 내용

The source is a 23-minute Korean walkthrough on the AgentOS YouTube channel (published 2026-11-15) of Lauren Tan's talk "All Code Is Slop (Except Mine)" at the AI Engineer conference. She works on Grok Bot, an agent desktop app (Electron), and is the author of the pstack plugin. "Slop" means low-quality output an AI produced carelessly.

Her thesis: an engineer's job is now to keep or raise code quality while output rises massively. She calls the method "trust": not blind trust, but investing in the agent's environment until you can trust it to do the right thing. It took her six months.

KO출처는 AgentOS 유튜브 채널의 23분짜리 한국어 해설 영상(2026-11-15 게시)이며, 원본은 AI Engineer 컨퍼런스에서 로렌 탄(Lauren Tan)이 한 발표 "All Code Is Slop (Except Mine)"입니다. 발표자는 에이전트 데스크톱 앱(Electron)인 Grok Bot을 만들고, pstack 플러그인의 저자입니다. "슬롭"은 AI가 대충 찍어낸 낮은 품질의 결과물을 뜻합니다.

핵심 주장은 엔지니어의 일이 이제 산출량이 크게 늘어도 코드 품질을 유지하거나 높이는 것이라는 점입니다. 방법의 이름은 "신뢰"입니다. 맹목적 신뢰가 아니라, 에이전트가 옳은 일을 한다고 믿을 수 있을 때까지 에이전트의 환경에 투자하는 것입니다. 그녀는 여섯 달이 걸렸다고 합니다.

Her concrete examples / 구체적인 사례

Ban what needs nuance

Codebase

React useEffect is easy to misuse, and agents misuse it. Grok Bot bans it in product code; it is allowed only inside the framework's own APIs. The problem is gone "categorically".

미묘해서 잘못 쓰기 쉬운 useEffect를 제품 코드에서 금지하고 프레임워크 내부에서만 허용합니다. 문제가 "범주째" 사라집니다.

Context through folders

Static analysis

Two top-level folders, one for Electron's main process and one for its renderer, with imports between them banned by a dependency checker and lint rules. Agents stopped causing UI jank by importing main-thread code.

최상위 폴더 두 개로 나누고 서로 가져다 쓰는 것을 의존성 검사기와 린트로 금지했습니다. 에이전트가 메인 스레드 코드를 가져와 화면을 버벅이게 하는 일이 없어졌습니다.

Comments as excuses

Prose

Agents wrote comments justifying quick fixes (timers patched over an architecture clash). The timers spread and the app slowed. Grok Bot bans 99 % of comments and adds lint errors that name the root cause instead.

에이전트가 땜질(타이머)을 정당화하는 주석을 썼고, 타이머가 퍼져 앱이 느려졌습니다. 주석 99%를 금지하고, 근본 원인을 알려 주는 린트 오류로 대신합니다.

Review evidence, not code

Verification

Agents run the app (Chrome DevTools protocol) using a "feature map" of every user-facing feature, and leave videos, screenshots and diagrams. TLA+ checks multi-device notification flows; Lean proves a virtual-list algorithm; property-based tests probe the UI.

에이전트가 모든 기능의 "기능 지도"를 보고 앱을 직접 실행해 영상·스크린샷·다이어그램을 증거로 남깁니다. TLA+로 알림 흐름을, Lean으로 가상 목록 알고리즘을 검증하고, 속성 기반 테스트로 UI를 시험합니다.

02The inverted pyramid / 거꾸로 선 피라미드

Her answer to "where should I spend time on the agent's environment" is an inverted pyramid, widest layer first. The top two layers are deterministic: they constrain what agents can do and force the right thing by default. Prose (rules files, skills, AGENTS.md) is a thin layer kept for judgment calls only.

KO"에이전트 환경의 어디에 시간을 써야 하는가"에 대한 답은 넓은 층부터 쌓은 거꾸로 선 피라미드입니다. 위의 두 층은 결정적입니다. 에이전트가 할 수 있는 일을 제한하고 기본값으로 옳은 일을 하게 만듭니다. 산문(규칙 파일, 스킬, AGENTS.md)은 판단이 필요한 것만 담는 얇은 층입니다.

Rule 1 · Every correction becomes a check

When you correct an agent, do not add a line to a rules file. Turn it into a lint rule, test, type or API change. A rule in code is reproducible; a rule in prose is a hope.

KO에이전트를 교정할 때 규칙 파일에 한 줄을 보태지 말고 린트 규칙·테스트·타입·API 변경으로 바꾸라는 것입니다. 코드 속 규칙은 재현되지만 산문 속 규칙은 바람일 뿐입니다.

Rule 2 · Fix the inner loop before automating it

If the loop that writes code produces slop, automating it produces more slop at higher token cost. Block new anti-patterns first, clean up old ones next, then make verification strong.

KO코드를 쓰는 안쪽 루프가 슬롭을 내면, 자동화는 더 많은 토큰으로 더 많은 슬롭을 만들 뿐입니다. 새 안티패턴부터 막고, 기존 것을 치우고, 검증을 단단히 하라는 순서입니다.

Four tests whose result depended on timing or the machine / 타이밍이나 기기에 따라 결과가 달라지던 테스트 4개

Proof tamper that changed nothing

protocol · identity-proof.test.ts · fixed in #59

The test "tampered" a hex challenge by setting its first character to f. One challenge in 16 already starts with f:

f3a91c0e… → f3a91c0e… (unchanged, still valid)

Over 400 proofs the old tamper changed nothing 31 times and the verifier accepted exactly those 31; with the fix it accepted 0. The verifier was right; the test was wrong.

첫 글자를 f로 바꿔 "변조"했는데 16번 중 1번은 이미 f라 바뀌지 않았습니다. 400회 중 31회가 무변경이었고 검증기는 정확히 그 31개만 수락했습니다. 검증기는 옳고 테스트가 틀렸습니다.

A price found inside a timestamp

grid · scene-route.test.ts · fixed in #57

The test checked that the response does not contain the price 900 by searching the whole JSON, which also holds a millisecond timestamp:

"at": 1795395390096

Reproduced by pinning the clock to that value, then fixed by leaving the timestamp out of the search.

가격 900이 없는지 JSON 전체에서 찾았는데, 밀리초 타임스탬프에 "900"이 들어 있었습니다. 시계를 그 값으로 고정해 재현한 뒤 타임스탬프를 검색에서 뺐습니다.

Waiting one tick for a slow import

grid · health-watchdog-alert-sns.test.ts · fixed in #59

The alert is published in the background after a dynamic import of the AWS SDK. The test waited one setTimeout(0); when the import was slower, the first test saw 0 alerts and the late alert landed in the next test. It turned main red after six green runs. Reproduced by delaying the mocked import 30 ms; fixed with vi.waitFor.

AWS SDK를 동적으로 불러온 뒤 알림을 보내는데, 테스트는 한 틱만 기다렸습니다. 불러오기가 느리면 알림이 다음 테스트로 새어 들어갔습니다. 6회 통과 후 main을 실패시켰고, 불러오기를 30ms 늦춰 재현한 뒤 고쳤습니다.

A test that only worked on one machine

grid · operator-scope-typing.test.ts · fixed in #57

It hard-coded one developer machine's absolute repository path. Anywhere else it failed, and in a second checkout on that machine it silently tested the other checkout's copy of the gate. It now finds the repository root from its own location.

한 개발자 기기의 절대 경로를 하드코딩했습니다. 다른 곳에서는 실패했고, 같은 기기의 다른 체크아웃에서는 엉뚱한 사본을 조용히 테스트했습니다. 이제 자기 위치에서 저장소 루트를 찾습니다.

07What matters / 중요한 점

  1. A check nobody runs is prose. 13 of our gates and nearly all tests were deterministic code that behaved like a rules file: correct, and not enforced. Wiring them in was the cheapest, largest step, and it paid off the same evening: a newly wired gate stopped a change to the frozen audit allowlist 80 minutes later.
  2. Turning checks on finds rot first. 28 tests were stale and 4 more depended on timing or the machine, and nobody knew. The cost was paid once, today.
  3. A green check can mean nothing. One gate checks 0 routes; one tamper test sometimes changed nothing. Ask what a check would catch, then break the code to prove it.
  4. Fix the inner loop before automating it. Auto-merge without review stays off: the talk's claim rests on verification depth we only started building today.
  5. Don't copy everything. Her 99 % comment ban fits her codebase; ours carries decision IDs in comments (grid/src ≈ 27 % comment lines). Remove only comments that make claims nothing enforces.
  1. KO아무도 실행하지 않는 검사는 산문입니다. 게이트 13개와 거의 모든 테스트가 결정적 코드인데도 규칙 파일처럼 작동했습니다. 옳지만 강제되지 않았습니다. 연결하는 것이 가장 싸고 큰 걸음이었고, 그날 저녁 바로 효과를 냈습니다. 80분 뒤 새로 연결한 게이트가 고정된 감사 허용 목록의 변경을 잡아냈습니다.
  2. 검사를 켜면 썩은 곳부터 보입니다. 낡은 테스트 28개와 타이밍·기기에 좌우되는 테스트 4개가 있었고 아무도 몰랐습니다. 그 비용을 오늘 한 번에 치렀습니다.
  3. 초록불이 아무 의미 없을 수 있습니다. 경로 0개를 검사하는 게이트, 가끔 아무것도 변조하지 않는 변조 테스트. 검사가 무엇을 잡는지 묻고, 코드를 망가뜨려 증명해야 합니다.
  4. 자동화 전에 안쪽 루프부터. 리뷰 없는 자동 병합은 계속 끕니다. 발표의 주장은 우리가 오늘 막 쌓기 시작한 검증 깊이에 기대고 있습니다.
