Godot C++ → Rust for the 3D view?

Verdict: no. Porting Godot to Rust would mean writing a new engine, and Noēsis has no C++ to migrate. Keep three.js. If Rust is wanted, start by compiling only the compute-heavy parts to WASM.

English한국어

EN1. Porting Godot itself

Fact (GitHub API, 2026-11-21)What it means
About 64 MB of C++ source, roughly 1.5–2 million lines (vendored third-party code included)A rewrite of a whole engine, not a translation. Many person-years of work.
Mature subsystems: Vulkan, GL and Metal renderers, physics, the editor, the import pipeline, about 6 platform targetsEach one is a project on its own scale.
Upstream is very active: last push 2026-11-20, about 120k stars, MIT licenceA Rust fork would fall behind at once and lose every upstream fix.
Rust engines already exist: Bevy (ECS, pre-1.0) and Fyrox (has an editor). Godot 4 already takes Rust code through godot-rust/gdext"Godot but in Rust" is already available without porting anything.

EN2. What Noēsis renders today

The whole 3D view is two files in dashboard/src/components/worldmap/: orbital-station-scene.ts (482 lines) and district-scene.ts (263 lines), 745 lines of three.js (0.160) in total. They live in the Next.js 15 / React 19 dashboard and are served on the web. No other dashboard file imports three.js.

So any engine change means replacing about 750 lines of TypeScript. There is nothing in C++ to migrate. Using three.js for the orbital 3D view is already a decision of the project.

EN3. The real options

OptionStrengthsCostsWhen it fits
A. Keep three.jsrecommendedSame language as the dashboard; small bundle (about 150 KB gzipped); already deployed; matches the 3D decisionEngine features such as physics or an editor are built by handNow, and for the scale we can foresee
B. Godot (C++) + Rust logic through gdextA full engine and editor; game logic in RustWeb export is tens of MB of WASM; threaded builds need COOP/COEP headers; gdext web support is still experimental; needs a new Grid → WebSocket → Godot data pathA native desktop client or heavy authoring tools
C. Bevy (pure Rust)ECS suits thousands of Nous; one language for server and client simulation code; WASM with WebGL2/WebGPUPre-1.0, with breaking releases every few months; no editor; UI is slower to iterateThe simulation core moves to Rust and must run the same on both sides
D. Rust → WASM for compute, three.js for renderingRust only where it is measurably faster (physics gate, simulation kernels); the renderer stays as it isA WASM boundary and one more build stepProfiling shows the browser CPU is the bottleneck

EN4. When a switch would be justified

Revisit B, C or D only when one of these becomes true:

  1. The scene holds many thousands of dynamic objects and per-frame simulation in the browser is too slow. Measure this first.
  2. A native desktop client is required.
  3. The backend and the viewer must share the same deterministic simulation code.

Recommendation: stay on three.js. If Rust is wanted, begin with option D, and only for code that profiling shows is slow.

사실 (GitHub API, 2026-11-21)의미
C++ 소스 약 64 MB, 대략 150만~200만 줄 (vendored 서드파티 코드 포함)번역이 아니라 엔진 전체를 다시 쓰는 일입니다. 수 인년(人年)이 듭니다.
성숙한 서브시스템: Vulkan·GL·Metal 렌더러, 물리, 에디터, 임포트 파이프라인, 약 6개 플랫폼하나하나가 별도 프로젝트 규모입니다.
업스트림이 매우 활발함: 마지막 push 2026-11-20, 스타 약 12만, MIT 라이선스Rust 포크는 즉시 뒤처지고 업스트림 수정을 모두 잃습니다.
Rust 엔진이 이미 있음: Bevy(ECS, 1.0 이전), Fyrox(에디터 있음). Godot 4는 godot-rust/gdext로 이미 Rust 코드를 받습니다포팅 없이도 "Rust로 쓰는 Godot"는 이미 가능합니다.

KO2. Noēsis가 지금 렌더링하는 것

3D 뷰 전체가 dashboard/src/components/worldmap/ 안의 파일 두 개입니다: orbital-station-scene.ts(482줄)와 district-scene.ts(263줄), 합계 three.js(0.160) 745줄. Next.js 15 / React 19 대시보드 안에 있고 웹으로 서비스됩니다. 다른 대시보드 파일은 three.js를 import하지 않습니다.

따라서 엔진 교체는 TypeScript 약 750줄을 바꾸는 일입니다. 마이그레이션할 C++ 코드는 없습니다. 궤도 3D 뷰에 three.js를 쓰는 것은 이미 프로젝트의 결정입니다.

KO3. 실제 선택지

선택지장점비용적합한 시점
A. three.js 유지권장대시보드와 같은 언어; 번들이 작음(gzip 약 150 KB); 이미 배포됨; 3D 결정과 일치물리·에디터 같은 엔진 기능은 직접 구현지금, 그리고 예측 가능한 규모까지
B. Godot(C++) + gdext로 Rust 로직완전한 엔진과 에디터; 게임 로직은 Rust웹 export가 수십 MB의 WASM; 스레드 빌드는 COOP/COEP 헤더 필요; gdext 웹 지원은 아직 실험 단계; Grid → WebSocket → Godot 데이터 경로 신규 구축네이티브 데스크톱 클라이언트나 무거운 저작 도구가 필요할 때
C. Bevy (순수 Rust)ECS가 수천 개 Nous에 적합; 서버·클라이언트 시뮬레이션을 한 언어로; WebGL2/WebGPU 기반 WASM1.0 이전이라 몇 달마다 호환성이 깨짐; 에디터 없음; UI 반복 작업이 느림시뮬레이션 코어를 Rust로 옮기고 양쪽에서 똑같이 돌려야 할 때
D. 연산은 Rust → WASM, 렌더링은 three.js측정상 더 빠른 곳에만 Rust(물리 게이트, 시뮬레이션 커널); 렌더러는 그대로WASM 경계와 빌드 단계 하나 추가프로파일링 결과 브라우저 CPU가 병목일 때

KO4. 전환이 타당해지는 조건

아래 중 하나가 사실이 될 때만 B, C, D를 다시 검토합니다:

  1. 장면에 동적 객체가 수천 개 이상이고 브라우저의 프레임당 시뮬레이션이 너무 느릴 때. 먼저 측정합니다.
  2. 네이티브 데스크톱 클라이언트가 필요할 때.
  3. 백엔드와 뷰어가 같은 결정론적 시뮬레이션 코드를 공유해야 할 때.

권장: three.js를 유지합니다. Rust를 쓰고 싶다면 선택지 D부터, 그것도 프로파일링으로 느리다고 확인된 코드에만 적용합니다.
