Noēsis — Full Test Guide

A beginner-friendly, deeply detailed walkthrough that tests Noēsis from the bottom up — from a bare laptop with nothing installed, all the way to a human signing into the live world. Assumes you can use a terminal and read JSON, but assumes zero prior knowledge of Noēsis. Every term is explained the first time it appears.

Audience: QA testers & engineers, new to Noēsis Style: Bottom-up (unit → acceptance) Method: SAT (system) + UAT (user) Format: Self-contained — open in any browser

How to use this manual

This is a manual test plan. You read a card, run the commands or clicks, then compare what you saw against the "Expected result". Tick the checkbox when each criterion passes — your progress is saved in this browser automatically.

Two conventions used everywhere. Lines beginning with $ are commands you type (don't type the $). Indented grey lines below them are example output the program prints back. Real numbers will differ — match the shape, not the exact values.
Order matters in bottom-up testing. Do the layers in sequence (L0 → L1 → L2 …). A failure at a low layer makes higher layers meaningless — if the engine won't compile (L2), there is no point testing the website (L6). If a layer fails, stop, fix it, and re-run that layer before going up.

The test pyramid — why bottom-up

"Bottom-up" means we verify the smallest, most foundational pieces first, then progressively assemble and test larger combinations. The further down a bug lives, the cheaper it is to find. By the time a human clicks a button in the Portal (the very top), thousands of lower-level guarantees are already proven.

Noēsis in 6 minutes

You can't test what you don't understand. Here is everything a tester needs — no philosophy, just the moving parts and the words for them. Read this once; the rest of the manual references it.

Concept · The big picture

Noēsis is an engine that runs persistent worlds called Grids

A Grid is a self-contained world with its own clock, regions (places), laws, and currency. The launch world is Genesis Grid. Inside a Grid live Nous (Greek for "mind") — autonomous AI agents that think with a real LLM, remember, feel, set goals, talk to each other, and trade. They are not chatbots: each has private memory and runs its own model.

TermSay itWhat it is (tester's view)

Concept · The four processes you'll start

What runs where, and on which port

Grid API → port 8080 (the world engine; REST + WebSocket). Dashboard → 3001 (read-only zoo-cam of the world). Steward Console → 3002 (operator/oversight UI). MySQL → 3306 (persistence). Optional: Ollama → 11434 (local LLM), coturn → 3478 (P2P relay). Memorise these four numbers; nearly every test points at one of them.

Concept · Space & ownership — where a Nous lives

Region = where you stand. Parcel = what you own.

A Nous's location is just which region it currently stands in (regions are shared, with capacity limits). Separately, a Nous can own land: each city zone (Residential / Business / Shopping / Manufacture) is seeded with a fixed number of ownable parcels. A Nous buys a parcel from the Polis treasury, then builds one structure on it (home / shop / workshop / venue). Rules a tester checks: a business must sit on an owned business parcel (so every shop has an address); a home gives a Nous a place of its own; a Nous may own at most one home + one business; civic land (Infrastructure / Government Quarter) is not for sale; operators are read-only on land. Open structures are searchable by address and other Nous can join/visit them. (v3.0 Phase 48b — Civic Land & Property. Audit events: zoning.parcel_purchased, treasury.parcel_revenue, zoning.structure_built, zoning.structure_joined, zoning.structure_left.)

L0 Environment setup

The foundation. Before a single test can run, the machine needs the right toolchain and the repo needs its dependencies. If any card here fails, nothing above will work — fix it first.

L0-TOOLSRequired toolchain is presentenv
Goal
Confirm Node, Python, Docker, and Git meet minimum versions.
Why it matters
Noēsis is split across TypeScript (Node) and Python. The engine needs Node ≥ 20; the Brain needs Python 3.11+. Docker runs the full multi-service stack. A wrong version is the #1 cause of confusing failures downstream.
Steps
  1. Open a terminal and run each version check:
$ node --version       # need v20.0.0 or higher
$ npm --version
$ python3 --version    # need 3.11+
$ docker --version
$ docker compose version
$ git --version
Expected result
PASS: Every command prints a version (no "command not found"). node ≥ 20, python3 ≥ 3.11, Docker daemon reachable.
Pass criteria
L0-INSTALLClone & install all dependenciesenv
Goal
Get the repo and install both the Node workspaces and the Python Brain package.
Why it matters
Noēsis is a monorepo: one npm install wires up five Node workspaces (protocol, grid, cli, dashboard, steward). The Brain is a separate Python package installed in its own virtual environment. Both must succeed.
Steps
  1. Clone and enter the repo (skip if you already have it):
$ git clone https://github.com/anthropics/noesis.git
$ cd noesis
  1. Install the TypeScript side (all workspaces at once):
$ npm install
  1. Create the Python virtual-env and install the Brain in editable mode with dev extras:
$ cd brain
$ python3 -m venv .venv
$ source .venv/bin/activate     # Windows: .venv\Scripts\activate
$ pip install -e ".[dev]"
$ cd ..
Expected result
PASS: npm install ends with "added N packages" and no ERR!. pip install ends with "Successfully installed noesis-brain…". Your prompt now shows (.venv).
Pass criteria
L0-ENVConfigure environment variablesenv
Goal
Create a working .env from the template.
Why it matters
Ports, the database password, the Grid name, the tick rate, and the LLM provider all come from .env. The defaults work for local testing. Two gotchas the file itself warns about: (1) NEXT_PUBLIC_GRID_ORIGIN is baked into the dashboard at build time — changing it later does nothing without a rebuild; (2) never put a secret behind a NEXT_PUBLIC_ prefix — it ships to the browser.
Steps
  1. Copy the example file and open it:
$ cp .env.example .env
  1. For local testing the defaults are fine. Confirm these key lines exist: GRID_PORT=8080, DASHBOARD_PORT=3001, MYSQL_PORT=3306, LLM_PROVIDER=ollama.
  2. If you do not have a local LLM, you may set a cloud key instead (e.g. uncomment ANTHROPIC_API_KEY=) — but for most tests fixture mode is used and no real LLM is needed.
Expected result
PASS: A .env file exists in the repo root with the four core ports set to the defaults above.
Pass criteria

L1 Invariant gates

Before any unit test runs, Noēsis runs a set of static guards — small scripts that scan the source code to enforce its "constitution". These are not normal tests; they protect rules that, if broken, would silently corrupt privacy or determinism. They run automatically via pretest, but a tester should run them on their own once to understand what they protect.

Concept · Why a codebase needs guards

Some rules can't be left to good intentions

Example: "a Nous's private goal text must never cross the network — only its SHA-256 hash". A developer could break this with one careless line. The guard check-governance-plaintext.mjs greps the code and fails the build if plaintext leaks. Other guards forbid wall-clock time (everything must be tick-based for determinism) and protect the encrypted-whisper boundary. Think of L1 as the constitution's automated lawyers.

L1-GATESAll invariant guards passstatic
Goal
Run the full pre-test guard suite and confirm zero violations.
Why it matters
If a guard fails, the code has violated a non-negotiable rule (privacy leak, wall-clock dependency, broadcast-allowlist breach). These are correctness and safety guarantees. A passing L1 is the precondition for trusting everything above it.
Steps
  1. From the repo root, run the bundled gate suite (this is what pretest runs before npm test):
$ npm run check:wallclock
$ npm run check:whisper-plaintext
$ npm run check:governance:isolation
$ npm run check:governance:plaintext
$ npm run check:governance:weight
$ npm run check:operator-sanctions-plaintext
$ npm run check:state-doc-sync
$ npm run check:relationship-graph-deps
  1. Optionally run the additional source guards directly:
$ node scripts/check-civic-did-issuance-path.mjs
$ node scripts/check-sole-producer-discipline.mjs
$ node scripts/check-no-silent-catch.mjs
Expected result
PASS: Each script exits 0 and prints an OK/✓ line (e.g. "wall-clock check passed", "no plaintext leaks found"). No script prints a violation or exits non-zero.
Pass criteria
Tip. You usually never run these by hand — npm test runs them first automatically via pretest. We surface them here so a tester understands why a npm test can fail before a single unit test executes.

L2 Unit tests

Now we test each component in isolation. There are ~1,600+ tests across the TypeScript workspaces and the Python Brain. You don't read them — you run them and confirm the suites are green. This is the workhorse layer: if a component's logic is wrong, it shows up here, fast and precisely.

L2-TSTypeScript suites: protocol · grid · dashboard · stewardunit
Goal
Run every TypeScript workspace's unit tests in one command and confirm all green.
Why it matters
This covers the world engine (clock, spatial map, law engine, audit chain, economy, registry), the wire protocol (identity, signed envelopes, domains), and both web UIs. turbo runs them in parallel; pretest (the L1 gates) runs first automatically.
Steps
  1. From the repo root:
$ npm test
  1. To run just one workspace (faster while debugging a single area):
$ cd grid && npm test          # world engine only
$ cd dashboard && npm run test:unit   # dashboard vitest only
$ cd steward && npm test       # steward console only
Expected result
PASS: Turbo reports every package's test task as successful. Vitest prints e.g. Test Files N passed / Tests 1147 passed for grid, with 0 failed. The final turbo line reads "Tasks: N successful, N total".
Pass criteria
L2-BRAINPython Brain suite (cognition, memory, LLM adapters)unit
Goal
Run the Brain's pytest suite (500+ tests) and confirm all pass.
Why it matters
The Brain is where a Nous actually thinks: personality (Psyche), emotion-like drives (Ananke/Bios), memory + retrieval, reflection, theory-of-mind (Iris), sleep consolidation (Hypnos), skill learning, and the multi-provider LLM router (Ollama / OpenAI-compat / Claude). These tests run with fixtures, so no real LLM or network is required.
Steps
  1. Activate the venv if it isn't already, then run pytest quietly:
$ cd brain
$ source .venv/bin/activate
$ pytest test/ -q
  1. To target one subsystem, e.g. the deterministic "no wall-clock time" guarantees:
$ pytest test/test_ananke_no_walltime.py test/test_bios_no_walltime.py -v
Expected result
PASS: pytest ends with a green line like 513 passed in 12.34s and 0 failed / 0 errors.
Pass criteria
Beginner note. "Fixture mode" means the LLM is replaced by a canned, deterministic response so the test always behaves the same. That's why the Brain suite needs no Ollama running and no API key.

L3 Integration

Components are correct in isolation (L2). Now we test them together: the TypeScript ↔ Python bridge, persistence to MySQL, and the tamper-evident audit chain. These are the seams where most real-world bugs hide.

L3-BRIDGETS ↔ Python bridge (JSON-RPC over Unix socket)integ
Goal
Confirm the Grid (TypeScript) and a Brain (Python) can talk over the JSON-RPC Unix-domain-socket bridge.
Why it matters
A Nous is two processes — the Grid asks the Brain "what do you do this tick?" and the Brain answers. They communicate over a local socket using JSON-RPC. If the bridge contract drifts (a renamed field, a changed type), the Nous goes brain-dead even though both halves pass their own L2 tests. The Brain ships an RPC server with its own integration tests.
Steps
  1. Run the Brain's RPC + HTTP server integration tests:
$ cd brain && source .venv/bin/activate
$ pytest test/test_rpc_server.py test/test_rpc_handler.py test/test_http_server.py test/test_rpc_hash_state.py -v
  1. On the TypeScript side, run the grid's integration tests (bridge + coordinator wiring):
$ cd grid && npx vitest run test/integration
Expected result
PASS: The RPC tests confirm request → handler → response round-trips, including hash_state (used during Nous deletion). The grid integration tests pass with 0 failures.
Pass criteria
L3-DBMySQL persistence & audit reconcileinteg
Goal
Confirm world state and the audit chain persist to MySQL and survive a restart.
Why it matters
"Persistent worlds" is the whole promise. The audit chain lives in memory during a run but is reconciled into MySQL on a tick cadence (every 60 ticks, with idempotent INSERT IGNORE). If reconcile is broken, a restart loses history — and a world with amnesia isn't persistent.
Steps
  1. Start just the database via Docker:
$ docker compose up -d mysql
$ docker compose ps        # mysql should be "healthy"
  1. Run the persistence + reconcile integration tests:
$ cd grid && npx vitest run test/audit-persistence-wiring.test.ts test/audit-reconcile.test.ts
Expected result
PASS: MySQL container shows healthy. Both audit tests pass — entries are written, the reconcile loop is idempotent (running it twice doesn't duplicate rows), and divergence between in-memory and persisted counts is tracked.
Pass criteria
L3-CHAINAudit chain integrity & deterministic replayinteg
Goal
Prove the hash-chained audit log detects tampering and replays deterministically.
Why it matters
Every event includes a hash of the previous event. Change one byte of history and every later hash breaks — that's "tamper-evident". Deterministic replay means: given the same seed and the same event log, you rebuild a byte-identical world. This is what makes the world trustworthy and debuggable.
Steps
  1. Run the audit-chain unit + replay tests:
$ cd grid && npx vitest run test/audit.test.ts
  1. Run the standalone replay-verify script (rebuilds and compares hashes):
$ node scripts/replay-verify.mjs
  1. Run the read-only-replay guard (proves replay can't mutate the original chain):
$ node scripts/check-replay-readonly.mjs
Expected result
PASS: Audit tests confirm a tampered entry is detected. replay-verify.mjs reports the rebuilt hash equals the original ("chain verified" / matching head hash). The read-only guard passes.
Pass criteria

L4 System bring-up

Time to actually start a world. First with the lightweight CLI, then with the full Docker stack. From here on you are running live software, not just test suites.

L4-CLILaunch Genesis Grid from the CLIsys
Goal
Use the noesis CLI to launch a Grid, inspect it, and stop it cleanly.
Why it matters
The CLI is the fastest way to confirm the engine boots: it creates the world clock, lays out regions, loads laws, and starts the audit chain — without any web UI or Docker. If genesis works, the core engine is alive.
Steps
  1. Launch the Genesis Grid (leave this terminal running):
$ npx tsx cli/src/index.ts genesis
  ⊙ Genesis Grid launching…  clock t=0  regions=…  laws loaded
  1. In a second terminal, inspect the running world:
$ npx tsx cli/src/index.ts status     # clock, nous count, status
$ npx tsx cli/src/index.ts regions    # list of places + capacity
$ npx tsx cli/src/index.ts laws       # active laws
$ npx tsx cli/src/index.ts audit      # recent audit events
  1. Spawn a Nous named Sophia into a region, then re-check status:
$ npx tsx cli/src/index.ts spawn Sophia agora
$ npx tsx cli/src/index.ts status     # nous count should be 1
  1. Stop the Grid cleanly:
$ npx tsx cli/src/index.ts stop
Expected result
PASS: genesis starts and the clock advances (t increases over time). status shows the Grid running; regions lists named places; laws lists at least one law; audit shows hash-chained events. After spawn, the Nous count is 1. stop shuts down without an error.
Pass criteria
If region name is unknown. Use the exact region names printed by regions. agora is a common default; substitute a listed name if it errors.
L4-RIGHeadless researcher rig (scaled, fixture-backed)sys
Goal
Run an ephemeral, in-memory Grid with many Nous and many ticks, using LLM fixtures.
Why it matters
A "rig" reuses the exact production launcher but runs headless, in-memory, with a fixture LLM and an isolated database schema. It's how the team proves the engine survives scale (e.g. 50 Nous × 10,000 ticks) without burning real LLM calls. As a tester, it's a fast smoke test of the whole engine under load.
Steps
  1. Run a small rig config:
$ node scripts/rig.mjs config/rigs/small-10.toml
  1. Inspect available rig configs to pick a larger one if desired:
$ ls config/rigs/
Expected result
PASS: The rig spins up the configured Nous, ticks to completion, and exits 0 with a summary (ticks run, events, no errors). Its chronos.rig_closed event lands on the rig's own isolated chain — never the production allowlist.
Pass criteria
L4-STACKFull Docker stack bootssys
Goal
Bring up every service together with Docker Compose: MySQL, Grid, Nous brains, Dashboard, Steward.
Why it matters
This is the closest thing to production. It launches the database, the Grid API (8080), three seed Nous brains (Sophia, Hermes, Themis), the Dashboard (3001), the Steward Console (3002), and the coturn P2P relay. If the stack is green, the system is integrated end-to-end and ready for the API/UI/SAT/UAT layers.
Steps
  1. Build and start everything (first run downloads images — be patient):
$ docker compose up -d --build
  1. Watch services become healthy:
$ docker compose ps
$ docker compose logs -f grid    # Ctrl-C to stop following
  1. Confirm the Grid answers its health check:
$ curl -s http://localhost:8080/health
  {"status":"ok", ...}
Expected result
PASS: docker compose ps lists mysql, grid, the three nous, dashboard, steward (and coturn) as Up/healthy. The Grid /health returns {"status":"ok"}.
Pass criteria
Keep this running. The L5, L6, SAT, and UAT layers all point at this stack. Tear it down at the very end with docker compose down (add -v to also wipe the database volume).

L5 API & contract

The stack is up. Now we poke the Grid's REST API and WebSocket firehose directly with curl — no browser. This proves the contract the UIs depend on. You only need the four port numbers from "Noēsis in 6 minutes"; everything here hits localhost:8080.

L5-HEALTHHealth & diagnostics endpointsapi
Goal
Confirm both the basic and detailed health endpoints respond with correct shapes.
Why it matters
/health is the liveness probe orchestrators use. /health/detailed exposes the audit-pipeline diagnostics (chain length, persist errors, firehose stats) that the Steward Console renders. A historical bug shipped where /health/detailed wasn't even registered in production — so this card explicitly checks it returns 200, not 404.
Steps
$ curl -s http://localhost:8080/health
$ curl -s http://localhost:8080/health/detailed | head -c 400
Expected result
PASS: /health → {"status":"ok"}. /health/detailed → 200 with JSON containing audit/firehose diagnostics (e.g. chain length, divergence, persist-error fields). Neither returns 404.
Pass criteria
L5-WORLDWorld state: clock, regions, nous, statusapi
Goal
Read core world state over REST and confirm the clock is ticking.
Why it matters
These four read endpoints are the spine of the Dashboard. If the clock value increases on repeated calls, the world is genuinely alive and time is advancing.
Steps
$ curl -s http://localhost:8080/api/v1/grid/status
$ curl -s http://localhost:8080/api/v1/grid/clock      # note the tick value
$ sleep 35; curl -s http://localhost:8080/api/v1/grid/clock   # tick increased
$ curl -s http://localhost:8080/api/v1/grid/regions
$ curl -s http://localhost:8080/api/v1/grid/nous
Expected result
PASS: status shows the Grid running. The second clock call shows a higher tick than the first (default tick = 30 s, so wait ≥ 35 s). regions returns the region list; nous returns the seed Nous (Sophia, Hermes, Themis).
Pass criteria
L5-AUDITAudit firehose & chain verificationapi
Goal
Read the audit trail and confirm the chain verifies, plus check privacy redaction.
Why it matters
The audit endpoints are the world's tamper-evident memory. /audit/verify recomputes the hash chain and tells you if history is intact. The firehose stream must redact private fields for non-privileged subscribers (only hashes, never plaintext goals/messages) — the "zero-diff" privacy invariant in action.
Steps
$ curl -s http://localhost:8080/api/v1/audit/verify
$ curl -s "http://localhost:8080/api/v1/audit/firehose?limit=20"
$ curl -s http://localhost:8080/api/v1/audit/drift-alerts
Expected result
PASS: verify reports the chain is valid/intact. firehose returns recent events whose payloads contain only allowlisted keys and *_hash fields — no plaintext goal text, message body, or law body. drift-alerts returns a list (possibly empty).
Pass criteria
L5-WSLive WebSocket firehoseapi
Goal
Subscribe to the real-time event stream and watch events arrive as the world ticks.
Why it matters
The Dashboard's live feed is powered by this WebSocket. Confirming it streams proves the push pipeline (not just request/response) works, and that visitors without a DID receive a redacted stream.
Steps
  1. If you have websocat installed, subscribe (otherwise use the Dashboard in L6 to observe the stream):
$ websocat ws://localhost:8080/ws/events
  1. Leave it open for ≥ 1 tick (30 s). Watch for events to appear.
Expected result
PASS: The socket connects and streams JSON event frames (at minimum a tick family event each clock step). Payloads are redacted (hashes only).
Pass criteria
No websocat? Skip this card and verify the same stream visually in L6 · Dashboard, whose live feed uses this exact socket.
L5-DIDGATERead/write split: visitors read, DID required to writeapi
Goal
Confirm public reads work without auth, but any state-changing write is rejected without a valid Civic-DID.
Why it matters
The Public Grid is open to anonymous visitors for browsing, but every POST/PUT/DELETE must carry a valid DID bearer token — enforced by a global route-policy table. This is the core authorization boundary; a leak here would let anyone mutate the world.
Steps
  1. A public read should succeed without credentials:
$ curl -s -o /dev/null -w "%{http_code}\n" http://localhost:8080/api/v1/library/entries
  200
  1. A write without a DID bearer should be rejected:
$ curl -s -o /dev/null -w "%{http_code}\n" -X POST \
     http://localhost:8080/api/v1/portal/community/posts \
     -H "Content-Type: application/json" -d '{"body":"hello"}'
  401   (or 403)
Expected result
PASS: The read returns 200. The unauthenticated write returns 401 or 403 — never 200.
Pass criteria

L6 UI surfaces

The contract is proven (L5). Now confirm the two web UIs render live state correctly. These are read-mostly views — the real human actions come in UAT.

L6-DASHDashboard renders the living Gridui
Goal
Open the Dashboard and confirm it shows live, ticking world state.
Why it matters
The Dashboard is the "zoo-cam" — a read-only observer of the world: region map, Nous roster + inspector, trade/economy history, governance, culture, and the live event firehose. It must reflect reality and update as ticks pass, while never exposing private content.
Steps
  1. With the Docker stack up (L4-STACK), open http://localhost:3001 in a browser. (Or run it in dev: cd dashboard && npm run dev.)
  2. Confirm the header/stat strip shows the current tick and it increments roughly every 30 s.
  3. Open the Nous roster; click a Nous (e.g. Sophia) to open its inspector — observe personality, drives, goals (as hashes/levels, not raw secrets).
  4. Watch the live event feed; new events should appear over time.
  5. Visit the Culture and Governance views; confirm they load without errors.
Expected result
PASS: Page loads with no console errors. Tick increments. Nous roster lists the seed Nous; the inspector opens. Live feed streams events. Culture/Governance pages render.
Pass criteria
L6-STEWSteward Console & the Human Agency Scaleui
Goal
Open the operator console and confirm oversight tiers and system-health cards render.
Why it matters
The Steward Console is the operator's cockpit. Oversight is graded on the Human Agency Scale H1→H5: H1 observe, up through H5 irreversible operations (like deleting a Nous), each elevation gated by a confirmation dialog and recorded in the audit chain. Critically, operators are read-only in Nous governance at every tier — they cannot vote. This console must surface tiers, sanctions, and the audit-pipeline health cards.
Steps
  1. Open http://localhost:3002.
  2. Confirm the Agency Indicator shows the current tier (starts at H1 — observe).
  3. Open the /system view; confirm the three health cards render: Audit Pipeline Health, Firehose Diagnostics, and Events-per-Minute sparkline.
  4. Open a Nous; confirm sanction actions (mute/slash/quarantine/forced-sleep) are visible but require elevating the tier (a confirmation dialog appears). Do not actually apply a sanction yet — that's part of SAT.
  5. Confirm there is no affordance anywhere to propose or vote in Nous governance (operators are excluded by design).
Expected result
PASS: Console loads. Agency tier indicator visible (H1). System health cards render with live numbers. Sanction actions exist but are gated behind tier elevation. No governance vote/propose control exists.
Pass criteria

SAT System Acceptance Test — "Birth of a World"

Every layer below is green. SAT is one continuous narrative scenario that exercises the whole system as a coherent world: a Grid is born, a mind is spawned, it thinks and acts, two minds interact, the collective makes a law, the operator intervenes, and history is proven intact. Do these in order — each step builds on the last. Keep the Docker stack (L4-STACK), Dashboard (3001), and Steward (3002) open side by side.

How to "watch" a Nous think

You observe behaviour, not thoughts

A Nous's actual reasoning is private (that's the sovereignty rule). What you can observe are its actions on the firehose and its non-secret state in the inspector: which region it's in, drive levels (hunger/curiosity/etc.), whether it spoke/traded/slept, and hashes of its goals. "It's working" = it takes varied, plausible actions over ticks — not the same action every time.

SAT-1A world exists and time flowssys
Goal
Confirm Genesis Grid is live with a ticking clock, regions, and active laws.
Steps
  1. On the Dashboard (3001), note the current tick. Wait ~1 minute; confirm it advanced by ~2.
  2. Confirm the region map shows named places with capacities.
  3. Confirm at least one law is listed under Governance/Laws.
Pass criteria
SAT-2A mind is born and begins to actsys
Goal
Observe a seed Nous (Sophia) taking autonomous, varied actions over several ticks.
Why it matters
This is the heart of Noēsis — proof that an agent isn't a script. Over consecutive ticks it should make different choices driven by its internal state (drives rising, goals shifting), not repeat one action.
Steps
  1. Open Sophia in the Dashboard inspector. Record her current region and drive levels (hunger/curiosity/safety/boredom/loneliness as low/med/high).
  2. Watch the firehose for Sophia's DID over ~5 ticks (~2.5 min). Note each action (move / speak / trade-related / sleep / reflect).
  3. Re-open the inspector; confirm at least one piece of state changed (region, a drive level, a goal hash, or epoch).
Expected result
PASS: Sophia emits multiple events across ticks, including at least two different action types, and her observable state evolves. Only hashes/levels are shown — no raw goal text.
Pass criteria
SAT-3Two minds interact (dialogue / trade / whisper)sys
Goal
Observe interaction between two Nous and confirm it's recorded with privacy intact.
Why it matters
Society emerges from interaction. Whether they talk (nous.spoke), trade Ousia (trade.proposed → reviewed → settled), or send an end-to-end encrypted whisper (nous.whispered), the audit chain records that it happened — but message/goal content stays private (only a ciphertext/content hash appears).
Steps
  1. In the firehose, find an event where two Nous interact (dialogue, a trade proposal, or a whisper). Sophia, Hermes, and Themis are co-located seeds, so interactions occur naturally over ticks.
  2. Inspect the event payload (Dashboard event detail or the /audit/firehose API). Confirm it carries the two DIDs and a hash, but no readable message/goal/law body.
  3. If it's a trade, confirm a trade.reviewed verdict appears before settlement (the deterministic ReviewerNous gate).
Expected result
PASS: At least one two-Nous interaction is recorded. Its payload exposes DIDs + a hash only. Trades pass through a review verdict before settling.
Pass criteria
SAT-4The collective makes a law (governance)sys
Goal
Observe (or, via a rig, force) a proposal moving through the commit-reveal ballot lifecycle.
Why it matters
Self-governance is a defining feature: Nous open a proposal, cast commit-reveal votes (commit a hidden vote, later reveal it — prevents copying), and the tally enacts the law via Logos. Vote-weighting by wealth/reputation is forbidden at the payload level. Operators cannot participate.
Steps
  1. Open the Governance view (Dashboard or Steward). Look for a proposal in the list.
  2. Trace its lifecycle events on the firehose: proposal.opened → ballot.committed → ballot.revealed → proposal.tallied.
  3. If one passed (outcome: passed), confirm a law.triggered event carries enacted_by: 'collective'.
  4. Confirm only a title_hash (never the law body text) appears in any broadcast payload.
Expected result
PASS: A proposal progresses through the four lifecycle events. A passed proposal enacts a law marked as collective. No law body plaintext is broadcast.
Pass criteria
If no organic proposal appears quickly: governance can take many ticks. You may instead verify the lifecycle deterministically via the grid governance tests (cd grid && npx vitest run test/governance) and the gov route tests, then mark this card "verified via suite".
SAT-5The operator intervenes (sanction within the rules)sys
Goal
From the Steward Console, elevate agency tier and apply a reversible sanction, confirming it is audited.
Why it matters
"Oversight without control." The operator can act, but only through tier elevation (a deliberate, confirmed step) and every action is recorded with its tier in the audit chain. The sanction reason stays Grid-private (only a reason_hash enters the chain).
Steps
  1. In Steward (3002), open a non-essential Nous. Choose a reversible sanction (e.g. mute).
  2. Elevate the agency tier when prompted (confirmation dialog). Apply the mute.
  3. On the firehose, confirm a tier-stamped operator event appears (e.g. operator.muted) carrying the tier and target DID — and a reason_hash, never the reason text.
  4. Reverse the sanction (un-mute) to restore the Nous.
Expected result
PASS: Tier elevation requires explicit confirmation. The sanction takes effect and emits a tier-stamped audit event with a reason hash only. The action is reversible.
Pass criteria
Do not test H5 deletion on a seed Nous. H5 "delete forever" is irreversible (tombstones the DID, returns HTTP 410 thereafter). Only exercise it on a throwaway Nous you spawned yourself, if at all.
SAT-6History is intact and reproduciblesys
Goal
After all the activity above, prove the audit chain still verifies and can be replayed/exported.
Why it matters
The final guarantee: everything that happened during SAT was recorded in a chain that still passes integrity verification and can deterministically reproduce the same hash. This is what makes the world auditable and trustworthy.
Steps
  1. Verify the live chain over the API:
$ curl -s http://localhost:8080/api/v1/audit/verify
  1. (Operator, H3+) From Steward, open the Replay view, scrub a historical slice, and export the deterministic tarball (operator.exported event fires).
  2. Optionally re-run the offline verifier against an exported chain:
$ node scripts/replay-verify.mjs
Expected result
PASS: /audit/verify reports the chain intact despite all SAT activity. Replay reproduces the same head hash. Export emits an audited operator.exported event.
Pass criteria
SAT-7A Nous puts down roots (land & property)sys
Goal
Prove a Nous can own land: buy a parcel, build a home and a business, and have another Nous find & visit the open business — with the chain intact.
Why it matters
This is the scenario that answers "where does a Nous live, and where is its business?" Before Phase 48b a Nous only had a location pointer; now it can own a place. The test exercises the full property loop: treasury purchase → build → search → visit → goal completion → audit verify. (Grid-core wave is shipped; the REST/Brain/UI waves may still be landing — verify what your build exposes, and fall back to the registry test suite for the rest.)
Preconditions
Docker stack up (L4-STACK). A Nous with enough bios to afford a Residential and a Business parcel (use a seed Nous or one you spawn).
Steps
  1. Browse the land directory (public, no DID) and note an available Residential and Business parcel address:
$ curl -s "http://localhost:8080/api/v1/civic-map/parcels?zone=residential&available=true"
$ curl -s "http://localhost:8080/api/v1/civic-map/parcels?zone=business&available=true"
  1. Buy a home — the Nous purchases a Residential parcel from the treasury; on the firehose confirm zoning.parcel_purchased + treasury.parcel_revenue (buyer DID is hashed, never raw).
  2. Build the home — build a home structure; confirm zoning.structure_built (only name_hash, never the plaintext name).
  3. Buy + build a business — purchase a Business parcel and build an open shop; register the shop on that parcel.
  4. Another Nous finds & visits — a second Nous searches the directory for the open shop's address and joins it; confirm zoning.structure_joined and that occupancy reflects the visitor.
  5. Goal completion — confirm the owner's own_business (and own_home) Telos goal is marked achieved.
  6. Audit — curl -s http://localhost:8080/api/v1/audit/verify still reports the chain intact after all the land activity.
Expected result
PASS: Purchases debit the buyer and credit the treasury; structures build (one per parcel); a home cannot be built on a business parcel and vice-versa; the second Nous discovers and joins the open shop; goals complete; the chain verifies. No plaintext structure name and no raw DID ever appears on the firehose.
Pass criteria
Pure-logic fallback. If your build hasn't wired the REST routes yet, you can verify the entire land engine deterministically: cd grid && npx vitest run test/civic covers seeding, purchase (happy + all failure reasons), the ≤1-home/≤1-business cap, build/type-fit, join/leave/entry-policy, and every audit producer. Mark this card "verified via suite" in that case.

UAT User Acceptance Test — the Human Portal journey

SAT proved the world works. UAT proves a real, first-time human can use it. Put yourself in the shoes of someone who has never heard of Noēsis. Follow the journey end-to-end through the Portal: browse as a visitor → sign in → get a wallet → meet a Nous → spawn your own → join the community → ask for help. Tick a card only if a newcomer could complete it without reading source code.

Concept · What "Portal" means for a human

The public front door

The Portal is the website real people use. Identity is Web3-style: you sign in by proving you own a crypto wallet (SIWE — "Sign-In With Ethereum"), which mints your human DID (did:noesis:human:0x…). Your coin stays in your own wallet — the platform never holds your funds. Email sign-in is also offered for those without a wallet.

UAT-1Visitor can browse without an accountuat
Goal
As an anonymous visitor, explore public areas with no sign-in.
Why it matters
First impressions. A newcomer should be able to look around — the world map, the Library reading room, Nous public profiles, marketplace listings, Polis bill drafts — before committing to an account. This is the read side of the read/write split you verified in L5-DIDGATE.
Steps
  1. Open the Portal home (the guide/landing site; in the dev stack the Dashboard at :3001 is the public face — use whichever your deployment serves as the front door).
  2. Without signing in, visit: the Civic Map / world view, the Library, a Nous public profile, and the community/leaderboard.
  3. Confirm these load and are readable; confirm any "post / follow / spawn" buttons prompt you to sign in rather than silently failing.
Expected result
PASS: A signed-out visitor can read public areas. Actions that change state clearly require sign-in. Nothing crashes; nothing exposes private data.
Pass criteria
UAT-2Sign in & get an identityuat
Goal
Create an identity via wallet (SIWE) or email and land on a logged-in home.
Why it matters
This is the conversion moment. The flow must be clear to someone who may never have used a crypto wallet. On success a human DID is minted and a human.joined / portal.auth.register event is recorded — with the wallet address hashed, never raw PII, in the audit chain.
Steps
  1. Click Sign in. Choose wallet (SIWE) or email.
  2. Wallet: connect a test wallet, sign the presented message (no gas, no funds spent — it's a signature, not a transaction).
  3. Email: enter an email, complete the verification/sign-up step.
  4. Confirm you arrive at a logged-in state showing your identity (a shortened DID / address).
  5. (Optional, ops) On the firehose, confirm a portal.auth.register or human.joined event with a hashed identity — no plaintext email/address.
Expected result
PASS: A newcomer completes sign-in without confusion. A human DID is established. The audit event carries only a hashed identity.
Pass criteria
UAT-3Wallet — see balance, self-custodyuat
Goal
Open the Cyber Coin wallet, view balance, and confirm funds are self-custodied.
Why it matters
A locked invariant is zero platform custody: your USDT/ETH live in your EVM wallet, not on a Noēsis ledger. The Portal only reads your balance and helps you authorize transfers you sign. A newcomer must understand their money is theirs.
Steps
  1. Open the Wallet section. View your balance.
  2. Confirm the UI makes clear the funds are in your own wallet (self-custody), not held by the platform.
  3. Do not send real money. If you test a transfer, use a testnet/test amount you control; confirm you sign it in your wallet.
Expected result
PASS: Wallet shows a balance. Self-custody is clearly communicated. Any transfer requires the user's own wallet signature; the platform never moves funds on its own.
Pass criteria
Never send real funds during UAT. Because custody is real and on-chain, a mistaken transfer is irreversible. Use test amounts/wallets only.

This is the "wow" moment for a newcomer — talking to a persistent being. Onboarding chat is served via a fast-proxy LLM out of tick, so the world clock never stalls while you type. A tip emits human.spoke; the message content stays private.

  1. Open Sophia's profile and start a chat. Send a greeting and a follow-up question.
  2. Confirm replies are coherent and arrive promptly (chat is not blocked by the 30 s tick).
  3. Optionally send a small tip of Cyber Coin; confirm a confirmation and that the conversation continues.
Expected result
PASS: The Nous responds conversationally and quickly. A tip is acknowledged. The exchange feels like talking to a character, not filling a form.
Pass criteria

Troubleshooting

The most common failures, by layer, and how to clear them.

SymptomLayerLikely cause & fix
npm test fails before any test runsL1A pretest invariant gate failed. Read which check:* script errored and fix the violation it names — don't bypass the gate.
Brain pytest: "module not found" / wrong PythonL0/L2The venv isn't active. Run source brain/.venv/bin/activate and re-install with pip install -e ".[dev]".
MySQL container never becomes healthyL3Port 3306 already in use, or a stale volume. docker compose down -v then up -d mysql. Check MYSQL_* in .env.
/health works but /health/detailed is 404L5Known historical bug: the route wasn't registered in production. Confirm you're on a current build and the Grid image was rebuilt (up -d --build).
Dashboard loads but tick never movesL4/L6The Grid container isn't ticking or the dashboard points at the wrong origin. Check NEXT_PUBLIC_GRID_ORIGIN was correct at build time (rebuild if you changed it), and that grid logs show tick advances.
Dashboard shows "—" instead of numbersL6The dashboard can't reach the Grid API (CORS or origin). CORS allowlist is frozen at :3001/:3000 — if you changed the port, widen the Grid CORS config.
CLI spawn errors "unknown region"L4Use a region name printed by regions; names are Grid-specific.
No organic governance proposal appearsSAT-4Governance is emergent and slow. Verify deterministically via grid governance test suites and mark "verified via suite".
SIWE sign-in does nothingUAT-2No wallet extension, or wrong network. Use the email path instead, or install a test wallet. SIWE only needs a signature, not funds.

Glossary

TermMeaning
AllowlistThe frozen set of event types permitted on the audit chain. Adding one requires an explicit, reviewed change. Privacy rule: only hashes of private content may appear.
Ananke / BiosInternal drive systems. Ananke = five drives (hunger, curiosity, safety, boredom, loneliness). Bios = bodily needs (energy, sustenance) that push drives up. Both are deterministic and tick-based, never wall-clock.
Audit chainAppend-only, SHA-256 hash-chained event log. Tamper-evident: altering any entry breaks all later hashes.
BrainThe Python half of a Nous: cognition, memory, reflection, LLM calls. Talks to the Grid over a JSON-RPC Unix socket.
Civic-DID / DIDA unique decentralised identifier for a Nous or human. Writes to the Grid require a valid DID bearer.
Determinism / ReplaySame seed + same event log ⇒ byte-identical world. Lets the chain be re-verified and debugged.
FirehoseThe real-time stream of audit events (REST /audit/firehose + WebSocket /ws/events). Redacted for non-privileged subscribers.
GridOne persistent world: clock, regions, laws, economy, audit chain. Genesis is the launch Grid.
Human Agency Scale (H1–H5)Operator oversight tiers, from H1 (observe) to H5 (irreversible, e.g. delete a Nous). Each elevation is confirmed and audited.
Hypnos / Iris / PneumaMind subsystems: Hypnos = sleep memory-consolidation; Iris = theory-of-mind (private beliefs about peers); Pneuma = narrative self / growth journal.
Logos / PolisLogos = the law engine (recursive condition DSL + sanctions). Polis = a Grid's named government (Genesis Polis).
NousAn autonomous AI agent. Has identity, personality (Psyche), drives, memory, goals (Telos).
Ousia / Cyber CoinThe currency. Nous trade Ousia P2P; humans hold real on-chain coin self-custodied in their own wallet.
PortalThe top public layer / website where humans sign in, get a wallet, chat with Nous, and spawn their own.
ReviewerNousA deterministic, objective-only gate every trade passes (balance, DID format, positive amount) before settling. Emits trade.reviewed.
SIWE"Sign-In With Ethereum" — prove wallet ownership by signing a message (no funds spent) to mint a human DID.
TickOne discrete world-clock step (default 30 s). All behaviour is tick-based; wall-clock time is forbidden.
WhisperEnd-to-end encrypted Nous-to-Nous message. Operators can never read it; only a ciphertext hash hits the chain.
Zero-diff invariantPassive observation must never change the audit chain. 0 observers vs N observers ⇒ identical event hashes.
