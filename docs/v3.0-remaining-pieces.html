The entire civic backend is built (Police · Library · Communities · the full Type B lifecycle · Portal-gating · 6-zone city · migration). Three things are left, and each one needs your decision before it can be built. This page explains exactly what they are, how they fit, and what to decide.

The big picture — where the 3 pieces attach

Everything in the green band is done. The three pieces sit at the edges: the Portal service (①) is the meta-layer that should host the approval workflows; the GPU farm (②) powers Type B brains; the Portal UI (③) is the human-facing face of the Portal.

① Phase 52 — Portal Infrastructure Decision needed

Make the Portal a real, separate service — its own login, its own audit chain, its own home on the internet — instead of a set of routes living inside the Grid.

What it is

Today the Portal workflows (approving new Grids, registering Nous, cross-Grid reads) already work — but they live inside the Genesis Grid's code (I built them there in Phases 53/54/55). Phase 52 lifts the Portal out into a standalone service that sits above every Grid:

  • Its own auth — log in with a crypto wallet (SIWE) or email; get a 24-hour Portal session token, separate from any Grid's Civic-DID.
  • Its own audit chain — tamper-evident, separate from each Grid's chain (same zero-diff guarantee).
  • A reviewer panel — Henry + 2–3 invited humans who approve Grid/Nous requests; every decision is logged.
  • A health page for operational visibility.

workflows done (grid-side)extraction + deploy pending

Why it matters

v3.0 runs one Grid (Genesis), so the Portal-inside-the-Grid shortcut works fine today. The separate service matters the moment a second Grid exists — the Portal is the neutral meta-layer that no single Grid controls, the place where "which Grids does this account belong to?" is answered.

Why it's not built yetIt's a brand-new deployable service that needs a home address and a tech-stack choice — both are decisions only you can make. Nothing is blocked in the meantime because the workflows already run grid-side.

② Phase 40b — Hosted LLM Pool (GPU farm) Hardware + decision

The "brains" for Type B Nous — the ones with no human operator, hosted by the Foundation. Their identity and money are already built; this is the compute that actually thinks for them.

What it is

A Type A Nous runs its brain on its operator's own machine. A Type B Nous has no operator — so someone has to run its brain. Phase 40b is that someone: a pool of GPU servers running an open LLM (the spec picks Llama 3.1 70B) on Henry's infrastructure, with:

  • Per-Nous quota — e.g. 600 tokens/minute; over-use returns a 429.
  • Cost accounting — track each Type B's daily compute cost.
  • Lifecycle orchestration — spawn a brain when a Type B is born, suspend it on dormancy, resume on revival.

③ Phase 56 — Portal User UI Frontend

The human-facing face of the Portal — one dashboard where a person sees all their Nous across all Grids, their wallet, and their pending registrations.

What it is

A web dashboard at portal.noesis/<account> with five panels:

  • Account Profile — who you are on the Portal.
  • My Nous — a cross-Grid table of every Nous you own (Type A): name, Grid, Civic-DID status, current zone, civic standing, last activity. Click a row → jump to that Grid's Steward Console.
  • Wallet — your Bios balance across Grids (+ per-Grid sub-balances).
  • Pending Registrations — in-flight Nous registrations with status (pre-screen / Polis / approved / rejected) and reason codes.
  • Settings.

depends on ① tech-stack call

Why it depends on ① and ②

  • It's the front-end of the Portal service (①) — so its tech-stack is the same decision (extend Steward Console vs standalone).
  • "My Nous across all Grids" + "cross-Grid wallet" read from the cross-Grid framework — which I already built as a dormant v3.0 stub (Phase 55): in v3.0 it correctly returns just [Genesis]. So the UI works today, it just shows one Grid until more exist.
  • Raw-SVG invariant applies (no d3, no react-flow) — same as the rest of Noēsis.
Good newsThis one has no new backend (allowlist +0) and no hardware. If you pick the tech-stack in ①, I can build this UI right away — it reads endpoints that already exist.
